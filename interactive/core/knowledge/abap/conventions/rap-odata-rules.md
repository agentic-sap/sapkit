# RAP & OData Rules — Field-Verified Failure Modes

**Scope.** This file lists the ways RAP artifacts fail **silently or misleadingly**. It covers the RAP generation only — a Service Builder (SEGW) service on an on-premise Gateway is a different model API with different failure modes and a different cache, and belongs to [`odata-gateway-rules.md`](odata-gateway-rules.md). Every rule below was verified on an S/4HANA on-premise system (ABAP 7.57) in real project work; SAP-standard samples are cited where they settled the question. When a rule names an exact checker message, match on the message, not on guesswork. When the RAP/EML or ABAP syntax itself is what you need, fetch the official ABAP Keyword Documentation through the [help-portal-fetch](../../../procedures/help-portal-fetch.md) procedure — and if that fetch cannot be completed, say so plainly rather than stating the syntax from memory.

## BDEF Authoring

**Anchor and masters (7.5x checker set).** The anchor CDS entity of a BDEF must be `define root view entity` — a non-root anchor is rejected at precheck (`... is not a root entity`). Declare `strict ( 2 )`; the checker then **forces** `lock master` and `authorization master ( global )` declarations, and the BIL needs two stubs to activate (`lock`, `get_global_authorizations`). Omitting `strict` activates but raises an ATC Prio-1 (`should be flagged as "strict"`). The warning `W333 READ/SAVER not implemented` does not block activation and may remain.

**Projection BDEF: `use etag` is NOT inherited.** A base BDEF's `etag master <field>` does **not** carry into a projection — the projection must state `use etag` itself (position: the line after `define behavior for <entity> alias <a>`, before the opening `{` — same slot as `etag master` in the base). Omission is completely silent: activation, syntax check, and ATC all pass, but `$metadata` emits `SAP__core.OptimisticConcurrency` as an empty `<Collection/>`, responses carry no `etag`, and If-Match / HTTP 412 optimistic locking never happens. Reference: SAP standard projection BDEF `C_BANKTP` (`use etag` on both entities).

**On-save triggers on a BO that does not expose `create`.** `validation ... on save { update; }` / `determination ... on save { update; }` is rejected (`The trigger "update" is only allowed in combination with "create" here.`). On an edit-only BO, use **field triggers** instead — `{ field f1, f2, ...; }`. Listing every editable field is semantically equivalent to an update trigger, and the handler signature (`FOR VALIDATE ON SAVE`) is independent of the trigger form, so the BIL needs no change.

**`managed ... with additional save` restricts saver hooks.** Only `save_modified` and `cleanup_finalize` can be redefined; redefining `cleanup` is rejected at precheck (`The method "CLEANUP" cannot be redefined ...`). Consequence to state explicitly when using shared handler↔saver buffers (`CLASS-DATA` etc.): `cleanup_finalize` covers only the normal-exit path, so buffer residue on the rollback/abort path is an **unclosable verification gap** in this form — closing it requires `unmanaged` (or `with unmanaged save`).

**Behavior pool identity.** Handler/saver locals derived from `CL_ABAP_BEHAVIOR_HANDLER` / `_SAVER` are only accepted inside a global class whose definition carries `FOR BEHAVIOR OF <bdef>`. A plain class shell — whatever its name — is rejected with `Local classes of "CL_ABAP_BEHAVIOR_HANDLER" can only be derived in ... a global BEHAVIOR class`; repair the class definition itself, don't fight the includes.

**No `deep` action parameter where the grammar has no `with hierarchy` (observed on 7.57).** `static action … deep parameter <entity> …` is refused with `The addition "deep" can be specified only if the behavior definition for "<entity>" has the attribute "with hierarchy"` — and on that release the attribute has no place in the grammar at all: the header accepts only `abstract | interface | managed | projection | unmanaged`, an entity-level `with` only `additional | control | unmanaged`, and `deep` in the body only as `deep mapping`. A write that takes many rows is therefore built as a **standard deep create** — a POST of the root with its composition children nested — rather than as an action. (Field-verified in real project work, 2026-09.)

**The fastest grammar check is the parser itself.** To learn what a slot accepts on the release in front of you, put a deliberately wrong token there and read the `"…" was expected` list the checker answers with. One probe settles what trying remembered variants one at a time does not — the list above was obtained exactly that way.

**Create the object, then write its source with `Update*`, then read it back.** `CreateBehaviorDefinition` takes no source: it creates the object with SAP's own template, not the behavior you meant — so write that with `UpdateBehaviorDefinition(source_code)` and read it back. `CreateServiceDefinition` writes, checks and activates `source_code` when it is given and leaves an empty, inactive shell when it is not (then `UpdateServiceDefinition`); where a step after the creation itself fails, the object already exists and the tool says so — continue with `UpdateServiceDefinition` instead of creating it again. Older bundles behaved differently, and in the BDEF case silently: [troubleshooting](../../../procedures/troubleshooting.md) § 8.

## Behavior Implementation — EML and Managed CREATE

**With external numbering, switch `%control` on for the key fields as well.** A managed `CREATE` moves only the fields whose `%control` flag is on into the buffer instance, so leaving the key control off — in a form where the caller is the one supplying the key — yields an instance whose key is initial although the value sits right there in the structure. The diagnostic fingerprint is **`failed` and `reported` both empty while `result` is empty too**: silence is not a rejection, because a gate that rejects always leaves a message behind. From that one root three symptoms fan out — the read-back returns zero rows (`READ ... WITH CORRESPONDING #( )` queries by the real key), create-skip guards all miss (the key that was marked is not the key the save phase sees), and validation messages point somewhere else entirely (a master lookup on an initial key reports a perfectly good value as invalid). Confirmation is cheap: if the statement setting `%control-<key>` to `mk-on` passes the syntax check, that flag exists — a component absent from the derived type is rejected outright. (Field-verified in real project work, 2026-08; a fresh-context review had passed over the same slot as "key — not required".)

**`failed` / `reported` from a nested `MODIFY ENTITIES` cannot be transferred into the handler's own.** The derived types differ, so neither `APPEND LINES OF` nor a shared method's CHANGING parameter will activate (`The type of "LS_REPORTED-<entity>" cannot be converted to the type of "REPORTED-<entity>"`). Consume the nested response **locally** for its verdict — to drop failed keys from `result`, for instance — and build the user-facing messages in the handler with `new_message( )` / `new_message_with_text( )`.

**A blank `DATS` is contamination rather than a mere format error, which makes the date guard a containment measure and not a validation.** The two empty representations of a date are set out in [`clean-code.md`](clean-code.md) § *Arithmetic and Initial Values*; `IS INITIAL` on its own lets eight spaces past. What raises the stakes here is what happens downstream — a row carrying a blank date breaks OData serialization with an HTTP 500, so a single such row can take the query service down. (The EML `CONV` path was observed to deliver spaces; that the OData `null` path delivers zeros is an inference, not a measurement.)

**Before the first run of a new guard, write down the value you would restore.** "It rejects, so the database is unchanged" holds only while the guard actually works — and the run that exercises a guard for the very first time is precisely the run in which it may not. In real project work (2026-08) a reject-path probe committed a ledger change under exactly that reasoning.

## CDS Artifacts

**SRVD accepts no comments.** A `//` line anywhere in a Service Definition fails precheck with `Comments are not supported and will be deleted on save`.

**DDLX (Metadata Extension): `@UI.facet` goes INSIDE the annotate block.** The only annotations allowed at entity level (outside `annotate view <e> with { ... }`) are `headerInfo` and `presentationVariant`. `@UI.facet` — nested or top-level — placed outside the block fails with `Annotation 'UI.facet.*' used at wrong position (wrong scope)`. Its correct slot is inside the block, **before the first element declaration** (SAP standard sample: `C_BANKTP` DDLX in `ODATA_BF_BANK_UI_MANAGE`). Also: an element listed in the block with **no annotation at all** is rejected (`must have at least one annotation`) — use `@UI.hidden: true` when you only need the element named. `annotate view` on a projection view entity is SAP-standard usage. Methodology note: an SAP sample that *lacks* a construct proves nothing about legality — judge a rejection by its error message, not by absence in one sample.

**Never pass conversion-exit fields straight through an OData-exposed view.** A field whose data element's domain carries a conversion exit (e.g. domain `KURSF` → exit `EXCRT`) makes Gateway metadata generation fail (`Do not use conversion exit ... here`, logged in `/IWBEP/ERROR_LOG`). Strip the DDIC reference with `cast( field as abap.dec( n, m ) )` (values are unchanged — verify once with a row-level comparison). On a V4 service one such field takes the **whole service** down, `$metadata` included — HTTP 500 with `Unwanted Feature at (Entity …, Property …)` — so check the domains of the fields you expose before exposing them, and expect it in bulk where a family of domains shares a customer exit. `ALPHA` is the exit that passes. (Field-verified in real project work, 2026-09.)

**A parent↔child composition activates in three passes.** Activating the root (carrying its composition) and the child (carrying its association to the parent) together fails, each reporting the other as a data source that does not exist or is not active. Activate the root without the composition, then the child, then add the composition to the root. (Field-verified in real project work, 2026-09.)

## OData Surface — Filtering and Metadata Judgment

**CHAR(1) flag fields map to `Edm.Boolean` by domain.** Gateway maps fields with domain `XFELD` or `X` to `Edm.Boolean`; a V2 `$filter` comparing them to a string literal (`eq ''`) fails with an Edm.Boolean type error — write `eq false` (blank ≡ false). The mapping is **per-domain, not per-ABAP-type**: another CHAR field whose domain is e.g. `BELNR` stays `Edm.String` and `eq ''` is valid there. Before writing filters, confirm the Edm type from `$metadata` (or the domain from `DD03L`).

**After changing annotations or a BDEF, clear the BACKEND cache before judging `$metadata`.** RAP local endpoints build their model in the backend, so `/IWBEP/CACHE_CLEANUP` is the one that matters — `/IWFND/CACHE_CLEANUP` (hub) alone shows **zero change** even when the fix landed. Run both. Diagnosis order when "$metadata didn't change": ① `DDANNOLOAD` (did the MDE merge?) → ② clear `/IWBEP/` + `/IWFND/` → ③ re-measure → ④ only then suspect the protocol surface. Skipping ② leads to re-suspecting correct code — field experience includes deleting and re-creating a healthy binding because of a stale cache.

**V4 UI annotations exist only under the `/srvd/` flavor — `/srvd_a2x/` omits them by design.** One binding serves two repositories whose URLs differ by a single path token:

```
.../sap/opu/odata4/sap/<srvb>/srvd/sap/<srvd>/0001/$metadata      ← UI flavor: UI.Facets, LineItem, SelectionFields, ... all emitted
.../sap/opu/odata4/sap/<srvb>/srvd_a2x/sap/<srvd>/0001/$metadata  ← A2X/API flavor: UI vocabulary absent (by design)
```

The schema namespace tells you which one you fetched (`...gateway.srvd....` vs `...gateway.srvd_a2x....`). Reading the A2X URL and concluding "annotations are missing" is a false diagnosis — and the observed RAP **V2** surface emits no UI vocabulary either (`sap:visible` absent even with `@UI.hidden` active; Fiori Elements consumption needs V4). When elimination keeps failing, put **"am I observing through the right instrument?"** on the candidate list.

**Binding contract (UI vs Web API) changes the real surface.** A `Web API` binding omits `Update_mc` / `sap:updatable-path` (row-level dynamic edit control), currency/UoM code lists, PDF/xlsx supported-formats, and value-help sets that a `UI` binding emits. The contract is visible as the Binding Type in the ADT header, or `srvb:category` in the binding XML (**0 = UI, 1 = Web API**). A `_UI` name suffix changes nothing, and the contract cannot be changed after creation — so it has to be right the first time. Don't judge publish state from IWSV entries in the package — Web API bindings leave none even when published.

**Pick the contract at creation.** Since the D-147 engine repair (server engine 1.4.0 / plugin 0.10.3) `CreateServiceBinding` takes `binding_category: "UI" | "WEB_API"` (default `WEB_API`, i.e. `srvb:category="1"` as before) and the response states which contract it created. *On older bundles* every binding came out as Web API, and a UI binding had to be created by hand in ADT. Offline-verified only, with a known live edge: the tool checks the requested binding type against `ListServiceBindingTypes` first, so on a system whose list carries no category-0 variant for the chosen protocol the call is refused at that gate rather than at creation. Confirm on first live use, and read back `srvb:category` on the binding rather than trusting the name.

## Publishing On-Premise (V4)

**The ADT publish button is not the only path — and in a Customizing client it is a blocked path.** `CL_RAP_SERVICE_BINDING_V4->publish_locally` refuses when the logon client's `T000-CCCATEGORY = 'C'` (message `RAP_SERVICES_ADT 021`, exception `publishing_in_custom_client`); unpublish is blocked the same way. That check exists **only in the ADT path**. The gateway transaction **`/IWFND/V4_ADMIN` → Publish Service Groups** (service group = the binding name, system alias `LOCAL`) performs the same underlying `publish_group` call without it — and per SAP Note 3101976 records to a customizing transport (ADT local publish creates a non-transportable local catalog entry), so the transaction is the **standard path**, not a workaround. V2 counterpart: `/IWFND/MAINT_SERVICE`. Related facts: a V4 service cannot be queried at all before publish (`/IWBEP/CM_V4_COS 014`); blocks are **layered** — client role is only one gate, an SCC4 change-recording restriction can still fail the publish underneath, so when a publish "is blocked", demand the exact message before concluding anything.

**Judge publish state from `srvb:published` on the binding and from nothing else.** Read it with `GetServiceBinding`. A `G4BA` object in the package appears when the binding is created and says nothing about publishing — it was seen beside a binding that read `srvb:published="false"` (field-verified in real project work, 2026-09) — and IWSV entries settle nothing either way (see above). A publish the server refuses, the Customizing-client block above among them, comes back from `UpdateServiceBinding` as a tool error since the D-152 engine repair (offline-verified only); *older bundles* answered `success: true` and carried the refusal only inside the payload (`SEVERITY: ERROR`), so on those read the payload, not the flag.

**A missing `srvb:allowedAction` is not a refusal.** Some systems never send that attribute on the binding XML. *On older bundles* `UpdateServiceBinding` read its absence as `UNKNOWN` and refused every publish and unpublish locally, while the same binding published from ADT immediately — a tool-side guard, not a server verdict. Since the D-147 engine repair (server engine 1.4.0 / plugin 0.10.3) the request is sent and the **server's** answer is returned as-is, flagged `allowed_action_known: false`; an attribute that is present and contradicts the request is still refused locally. `DeleteServiceBinding`'s best-effort unpublish behaves the same way. Offline-verified only — confirm on first live use, and where the server does refuse, that refusal is real.

## Writing Through a V4 Service

**A V4 write that fails with HTTP 500 before any of your ABAP runs may be the virus-scan check.** On a system with no active virus-scan profile, a V4 request that carries a binary property or nested children — a deep create, for one — is refused with `/IWBEP/CM_V4H_COS/001` (the upload virus-scan profile `/IWBEP/V4/ODATA_UPLOAD` is not active), while reads of the same service keep working, because a request with neither never reaches the scanner. SAP provides for a system without a scanner: the switch `VIRUS_SCANER_IGNORED` (SAP's spelling) in table `/IWBEP/C_V4_SETT`, also set through `/iwbep/cl_v4_settings_dba=>set_is_virus_scan_ignored( abap_true )`. It does not switch scanning off — it stops treating the absence of a configured scanner as an error, and a scanner configured later is used. The table is client-dependent and the value is cached statically, so sessions already running keep the old value. It is a system setting: put it to the system owner rather than changing it from the session. (Read off SAP's `/IWBEP/CL_V4_VIRUS_SCANNER`; field-verified in real project work, 2026-09.)

**To get computed rows back from a create, send the create and a read in one `$batch`.** The two obvious routes are closed. The gateway refuses `POST` with `$expand` (HTTP 501, `SADL_GW/041`), and a RAP create answers only with the children the request itself created, so rows the implementation computes are not in the response either way. A `$batch` is one HTTP request and so one ABAP session: a `POST` in a changeset followed by a `GET` in the same batch sees what the create left in a session buffer (`CLASS-DATA`), while the same `GET` sent as a separate request finds the buffer empty. (Field-verified in real project work, 2026-09.)

**Percent-encode the request line of every `$batch` part.** A part's relative URI is a real HTTP request line, so a space or a quote in it — `$filter=ReqId eq '…'` — fails with `/IWCOR/CX_OD_URI_SYNTAX_ERROR`. Write `%20` and `%27`. (Field-verified in real project work, 2026-09.)

## Wrapping an Existing RFC Function Module

**An amount the function module already converted for display gets converted a second time.** A module that returns amounts already shifted to their display form (through `CURRENCY_SAP_TO_DISPLAY`, for one) hands RAP a value that `@Semantics.amount.currencyCode` then shifts again by the currency's decimals in `TCURX` — ×100 for a currency without decimals ([clean-code](clean-code.md) § Currency Amounts). Convert back to the internal amount in the query implementation; every read wrapper over such a module hits it. A character-typed amount field (a batch-input field, for one) is not shifted and must not be given a currency annotation. (Field-verified in real project work, 2026-09.)

**A custom query needs an exception class of its own to refuse a call.** `CX_RAP_QUERY_PROVIDER` is abstract and cannot be raised, so a query that must reject a request — a mandatory filter missing, for one — needs its own subclass. Without it the request ends in an empty result, which the caller cannot tell from "no data". (Field-verified in real project work, 2026-09.)

**A function module that issues `COMMIT WORK` cannot run inside the RAP LUW.** Read its source before wrapping it: if it commits — directly, or through what it calls, such as a batch-input `CALL TRANSACTION` — call it with `DESTINATION 'NONE'`, which runs it in a session and LUW of its own; if it does not, call it locally. State the cost with the design: what that call posts is not rolled back with the RAP transaction, so the design assumes one posting per request, and such requests must not be grouped into one `$batch`. (Field-verified in real project work, 2026-09.)
