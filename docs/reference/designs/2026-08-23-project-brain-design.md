## 1. 문제의 정의

- **대상**: 계획→개발 사이클(이하 "판")이 10회 이상 반복되며, 세션/컨텍스트가 수시로
  초기화되는 AI 에이전트 주도 프로젝트.
- **증상 3종**: ① 못 찾음(있는 문서를 안 읽음) ② 빼먹음(알던 규칙을 그 순간 안 지킴)
  ③ 잘못 읽음(찾아 읽고도 낙관적으로 해석).
- **핸드오프 문서 단독이 반드시 실패하는 이유** — 새는 곳이 세 군데고 원인이 다 다르다:
  1. **쓰기 누락** — 핸드오프는 죽기 직전의 컨텍스트가 쓴다. 자기가 이미 잊은 것은
     원리적으로 쓸 수 없고, 문서 갱신은 본작업과 경쟁하는 부업이라 밀린다.
  2. **읽기 누락** — 다음 세션이 검색으로 찾아야 하는 구조면 못 찾는 게 정상이다.
     검색은 확률적이다.
  3. **해석 실패** — 찾아 읽어도 낙관적으로 읽는다. (실사고: sapkit 대장의 "증거
     대기"를 완료로 오독 — 2026-08-12, 대응 결정 D-082는 08-13.)
- **망각의 2종 구분** (대책이 완전히 다르다):
  - **세션 간 망각**: 새 세션이 이전 상태를 모른다. → 문서 체계(재개점·큐·결정 로그)로
    잡는다. sapkit은 이건 거의 해결했다.
  - **세션 내 망각**: 여러 시간짜리 판 도중, 시작 때 읽은 규칙이 컨텍스트 희석·요약으로
    사라진다. → **문서로는 못 잡는다** (문서는 읽는 시점에만 작동). 기계(훅)와 적용
    시점 재주입으로 잡는다. **sapkit에서 지금 남아 있는 망각의 대부분이 이쪽이다.**

## 2. 공통 원리 — 세 대상 모두에 적용

### 2.1 제1원칙: 레포가 기록하는 것은 다시 쓰지 않는다 — 포인터만

프로젝트는 세컨드브레인과 달리 **원본이 이미 안에 있다**: 코드가 무엇인지는 코드가,
무엇이 변했는지는 git 이력이, 무엇이 참인지는 시험·게이트가 기억한다. 여기에 지식
창고를 또 지으면 이중 저장 → 드리프트 → 큐레이션 노동, 즉 세컨드브레인의 무게가
그대로 재현된다. 산문으로 새로 쓸 것은 **코드가 못 담는 4종뿐**:

| 종류 | 내용 | 형태 |
|---|---|---|
| **왜** | 결정과 기각한 대안 | append-only 결정 로그 |
| **상태** | 지금 어디까지 왔나 | 재개점 문서 (작게) |
| **계획** | 다음이 뭔가 | 큐 |
| **경고** | 미래의 오독 방지 | 오독이 날 자리에 ⚠ 인라인 |

(aegis의 K-atom 입장 게이트가 같은 원칙을 이미 명문화하고 있다: "이 레포의 코드·
시험에서 유도 가능한 것은 기록하지 말고 포인터를 남겨라 — 드리프트할 수 있는 사본은
절대 금지.")

### 2.2 "모든 맥락을 안다"의 정의

모든 맥락을 **항상 로드**하는 게 아니라 **어떤 맥락이든 두 홉 안에 도달 가능**한 것.
매 세션 즉답돼야 하는 질문은 셋뿐이다 — ① 여기가 뭐 하는 프로젝트인가 ② 지금 어디까지
왔나 ③ 다음이 뭔가. 넷째(왜 그렇게 정했나)는 주소만 알면 된다.

### 2.3 4층 구조

| 층 | 담는 것 | 세션당 무게 | 쉬운 비유 |
|---|---|---|---|
| **핫** — 매 세션 자동 주입 | 정체성 30초 + "X 전엔 Y를 읽어라" 라우팅 (CLAUDE.md류) | 수 KB, **상수** | 출입문에 붙은 1장짜리 안내문 |
| **웜** — 세션 시작에 1회 | 재개점 + 큐 머리 (HANDOFF류) | 수 KB, **상수** | 책상 위 "오늘의 메모" 1장 |
| **콜드** — 주소로 도달, 필요할 때만 | 결정 로그 원문·설계서·아카이브·git·코드 | 무제한인데 **주입 0** | 서랍 속 서류철 |
| **반사** — 읽지 않아도 작동 | 게이트·CI·훅 | 토큰 0 | 과속방지턱, 자동 잠금문 |

**설계 규칙**: 각 사실마다 "산문보다 아래층에 둘 수 있는가?"를 묻는다. 기계(반사)로
지킬 수 있는 것을 산문(핫/웜)에 두면 반드시 썩거나 까먹는다.

### 2.4 무게의 척도

**무게 = 매 세션 주입되는 토큰 + 사람(또는 모델)이 손으로 갱신해야 하는 파일 수.**
저장 바이트가 아니다. (sapkit D-040의 척도를 일반화한 것.) 이 척도로는 결정 수백
개를 "아는" 두뇌도 가볍게 유지할 수 있다 — 콜드 층은 아무리 커도 무게 0이다.
세컨드브레인이 무거운 이유는 캡처 파이프라인·임베딩 인프라·큐레이션 노동인데,
프로젝트 두뇌는 셋 다 필요 없다(원본 내재 + 주소 회수 + grep 보조).

### 2.5 회수는 검색이 아니라 주소로

검색(시맨틱·키워드)은 확률적이고, 고정 주소(정해진 파일, 정해진 절)는 결정적이다.
**로드베어링 사실일수록 고정 주소로 옮긴다.** 검색은 리프 디테일의 보조 수단으로만.
"제대로 못 찾는" 문제의 근본 대책이 이것이다 — 찾게 하지 말고 박아 둔다.

### 2.6 경계선 법칙 (Q5 확정 · 독립 리뷰로 정밀화)

**관찰**: 산문만 지키는 규칙은 반복 위반된다(백틱 사고 2회, 셸 선택, 보고 규약,
문서 계약 — 전부 산문 영역). 기계가 지키는 영역은 위반이 드물다. **그러나 "기계
영역은 무사고"라는 강한 형태는 성립하지 않는다** (v1의 과장 — 리뷰 차단 ③): sapkit
실측으로 게이트가 거짓 red를 낸 사고(엔진 게이트 동시 실행)와 **훅 자체가 마찰을
만든 사고**(tdd-guard가 엔진 휴면으로 deny에 못 가고 대화 `ask`만 남겨 2026-08-02
등록 제거됨 · 훅 `ask`는 권한 모드를 덮어 오토 모드에서도 승인창을 띄우고 그 원인이
훅이라는 것 자체가 한 번 오귀인됨)가 있다.

따라서 법칙의 정확한 형태는: **산문은 반복 위반을 못 막고, 기계는 막되 공짜가
아니다.** 기계화안은 다음을 함께 제시해야 승격된다 — 오탐 비용 추정 · 마찰
예산(`ask` 최소화) · 비상 우회 경로(훅이 틀렸을 때 끄는 방법) · fail 정책
(크래시 시 무인/대화 분기 — sapkit `block-dangerous-bash.py`의 백스톱이 선례).

> **승격 규칙 (개정)**: 같은 행동 사고 **2회 = 기계화 후보 등재**, **3회 = 의무
> 기계화**. 단 **파괴적 사고(내용 손실·실데이터 유출급)는 1회로도 즉시 기계화**.
> 어느 경우든 위의 비용면 4항을 갖춰야 승격이 성립한다.

### 2.7 세션 내 망각의 대책 — 적용 시점 재주입

여러 시간짜리 작업에서 시작 때 읽은 규칙은 중반에 사라진다. 사람 조직의 해법과
같다 — 수술실은 "아침 교육"이 아니라 **수술 직전 체크리스트**를 들이댄다. 구현 3종:

1. **훅**: 실수하려는 순간 기계가 차단 (최강, 기계화 가능한 것만 — §2.6 비용면 포함).
2. **디스패치 동봉**: 서브에이전트를 보낼 때마다 그 작업에 해당하는 규칙 슬라이스를
   프롬프트에 실어 보낸다 (서브는 어차피 새 컨텍스트라 자연스러운 재주입 지점).
   ⚠ 이 비용은 §2.4의 "상수" 밖이다(디스패치 횟수 × 슬라이스 크기) — 슬라이스는
   **해당 작업에 적용되는 규칙만, 상한 수십 줄**로 제한하고, 교환비(서브 재작업
   1회 비용 ≫ 슬라이스 토큰)로 정당화한다. §2.10-2의 상수 시험은 핫+웜에만 건다.
3. **phase 경계 재정박**: 판의 단계가 바뀔 때 재개점을 미니 갱신하며 규칙을 되읽는다.

### 2.8 완료의 정의와 보고 규약

- **완료 = 기계 확인 + 새-컨텍스트 리뷰** 둘 다. 도구의 성공 응답은 어느 쪽도 아니다.
- **상태 어휘를 고정**하고 금지 해석을 명문화한다 (예: "증거 대기를 완료로 읽지
  않는다").
- **보고에는 분모**: "3종 완료"가 아니라 "156/186, 미룬 것 30과 그 이유". "다음 한
  걸음"만 보고하면 전부 끝난 것으로 읽힌다 (2026-08-12 실사고).

### 2.9 사고→구조 루프

처음부터 완벽한 설계는 불가능하다. 갈림길은 사고 유무가 아니라 **사고를 구조로
전환하는 루프의 유무**다: 사고 발생 → ① 오독이 났던 바로 그 문서 위치에 ⚠ 경고
인라인 ② 가능하면 기계(훅/게이트)로 승격 (§2.6 요건 충족 시) ③ 결정 로그에 박제.
이 루프가 있으면 반복할수록 단단해진다.

### 2.10 성공 판정 시험 2개

1. **새 세션 복원 시험**: 컨텍스트 0의 새 세션이 파일만 읽고 §2.2의 세 질문에
   정답하는가. 더듬는 지점이 곧 문서의 구멍이다. ⚠ **채점자는 반드시 새
   컨텍스트여야 한다** — 수술·작성을 한 세션이 스스로 치면 이미 맥락을 알고 있어
   무효다 (이 프로젝트의 품질 모델인 새-컨텍스트 리뷰가 그 자리다).
2. **무게 상수 시험**: 프로젝트가 자라도 **핫+웜의** 주입 바이트와 손 갱신 파일 수가
   상수로 머무는가. 자라고 있다면 콜드로 이사가 밀린 것이다. (디스패치 동봉 비용은
   §2.7-2대로 별도 계상.)

### 2.11 llm-wiki 구조의 채택 범위 (Q6)

Karpathy의 llm-wiki 요지: 3계층(**불변 raw sources** / LLM이 생성·유지하는 합성
**wiki** / 규칙 **schema**) + `index.md`(전 페이지 인덱스) + `log.md`(append-only
타임라인) + Ingest·Query·**Lint**(모순·고아 페이지·구식 주장 검출) 워크플로. 핵심
통찰 — "지루한 부분은 부기(bookkeeping)인데, LLM은 지루해하지 않는다."

**이 설계와의 관계: 뼈대는 이미 같다.** 사용자 지적대로 llm-wiki의 기본 구조는
무겁지 않다 — 그리고 그 구조는 이 설계에 이름만 다르게 이미 들어 있다:

| llm-wiki 요소 | 이 설계의 대응물 |
|---|---|
| schema (Karpathy 본인의 예시가 CLAUDE.md·AGENTS.md) | 핫 층 (§2.3) |
| log.md — append-only 타임라인 | 결정 로그 (DECISIONS/ADR) |
| index.md — 전 페이지 한 줄 인덱스 | 핫·웜 층의 포인터/라우팅, 콜드 인덱스 |
| Lint | 기계 검사층 (링크·신선도·append-only 검사) |
| Ingest | wrap — 세션 마감 시 지식 회수·문서 갱신 |
| "부기는 LLM이" | 문서 갱신·이사·링크 관리를 세션 마감 의식에서 모델이 수행 |

**추가 채택 — 콜드 층의 위키화 (성장 후 선택지).** 결정·판 기록이 수백 항목으로
자라면(sapkit은 이미 D-132), 아카이브를 시기별 분철로만 두지 말고 llm-wiki식으로
조직한다: 주제별 합성 페이지(예: "엔진 교체의 전 역사 — D-079·D-095·D-101 종합")
+ 교차 링크 + 콜드 전용 `index.md`. 규칙 둘:

1. 합성 페이지는 반드시 원본 항목(D-번호 등)을 인용한다 — **정본은 여전히
   append-only 로그**이고, 위키 페이지는 언제든 재생성 가능한 파생물이다.
2. 부기(페이지 생성·링크 갱신·모순 후보 보고)는 세션 마감 의식에서 LLM이 수행한다.
   검사층에는 **고아 문서 검출**(어디서도 링크되지 않는 문서)을 추가한다.

**채택하지 않는 것 — 경계 기준은 "원본의 불변성".** llm-wiki가 작동하는 전제는
raw sources 불변("출처는 절대 수정하지 않는다")이다. 그 전제가 깨지는 곳에는 얹지
않는다:

- **상태(핫/웜)의 위키화 금지** — 재개점·큐를 여러 페이지로 흩으면 회수가 다시
  확률화된다(§2.5 위반). 상태는 고정 주소의 단일 파일로 유지한다.
- **코드의 합성 페이지 금지** — 코드는 매 커밋 변하는 원본이라, 코드를 요약한 위키
  페이지는 곧바로 드리프트 사본이 된다(§2.1 위반). 코드의 인덱스는 코드 자체 +
  grep이고, 산문은 File map 한 줄 포인터까지만 허용.
- 외부의 **불변** 원본(논문·규정·표준 문서)을 많이 참고하는 프로젝트라면 콜드 층에
  `raw/` + `wiki/` 소구조를 여는 것은 허용 — 그건 llm-wiki의 원래 용도 그대로다.

결론: **세컨드브레인에서 버린 것은 인프라(임베딩·캡처 파이프라인)와 노동(사람
큐레이션)이지 구조가 아니다.** llm-wiki의 기본 구조는 이미 이 설계 안에 있고, 새로
가져올 것은 콜드 층 위키화 하나 — 그것도 기록이 수백 항목 규모로 자란 뒤에 여는
선택지다.

**공통 설계 요건 (§2.6 비용면)**: fail 정책(무인/대화 분기 백스톱 —
`block-dangerous-bash.py` 선례) · 비상 우회 경로 · `ask` 최소화(훅 ask는 권한
모드를 덮어 오토 모드에서도 승인창 — 실제 오귀인 사고 있음) · 판정 케이스
음성시험(막을 것을 막고, 정상 명령을 안 막는지).

구현 규모: ⓐⓔⓕ 반나절 (v1의 "각 30~60줄" 추정은 fail 정책·음성시험 포함 시
낙관적이었다 — 리뷰 지적 수용).

### 3.2 처방 2 — HANDOFF·RUN-PLAN 다이어트 수술 (근본, 대수술)

**원칙: 삭제가 아니라 이사** (append-only 정신 유지).

**착수 순서는 RUN-PLAN 먼저, HANDOFF 나중** (v1의 역순 — 리뷰 권고 수용):

- **RUN-PLAN (쉬움)**: L1~84가 이미 "큐 + 규약"이고 L85 이후 1,880줄이 판별 브리프
  전량이다. 큐 자체가 전 판 완료 상태라 브리프 전부가 아카이브 가능하고, 참조가
  산문 §번호가 아니라 판 이름이라 참조 파손 위험이 낮다. 사실상 한 번의 절단 —
  여기서 이사 절차·아카이브 조직을 먼저 검증한다.
- **HANDOFF (어려움)**: 살아있는 것(L74 부채·L103 다음 등)과 완료 판 기록(L111~
  L1160, 판M2-c~판5)이 블록인용(`> `) 안에 **교차 배치**돼 있어 발라내기가 필요하다.
  **블록인용 접두어는 유지한 채 이사한다** — 접두어를 떼면 "내용 무변경 순수 이동"
  diff가 성립하지 않는다.

| 파일 | 남기는 것 (수술 목표) | 이사하는 것 → 목적지 |
|---|---|---|
| `HANDOFF.md` | 재개점 블록 · 현재 상태표 · 부채 목록 · §8 불변 규칙(또는 CLAUDE.md로 통합 — 검토 포인트 ①) · 머신 환경 (**목표 300줄 / 기계 상한 500줄**) | 완료 판 기록 전부 → `docs/reference/handoff-archive/` — **원래 § 구조·번호를 보존해 이사** |
| `docs/RUN-PLAN.md` | 판 큐 · 현행 판 · 판 규약 (**목표 200줄 / 기계 상한 300줄**) | 판별 브리프 전량 → `docs/reference/run-archive/` |

(목표는 수술 결과, 상한은 §3.2-검증 ④의 게이트 문턱 — 버퍼를 둔 한 쌍이며 임계값은
이 둘뿐이다. aegis 기존 수치(core doc ~300줄·handoff 10KB)와의 단일화는 §4.2 스펙
개정 항목.)

**참조 인벤토리 선행 — v1의 검증안(check-links.mjs)은 폐기한다** (리뷰 차단 ④):
규정 호출(`check-links.mjs interactive`)의 사정거리에 루트·`docs/`가 없고, 실제
참조는 앵커 링크 0건에 **산문 § 번호**라 어떤 링크 검사기도 볼 수 없다. 절차:

1. `git grep`으로 HANDOFF·RUN-PLAN 참조 전수 인벤토리. 확인된 살아있는 산문 참조:
   `docs/ARCHITECTURE.md:159·161` · `docs/PRD.md:107` (둘 다 "HANDOFF §8" — 그리고
   R1에서 삭제된 `.harness/RULES.md`도 함께 가리키는 **이미 죽은 참조**: 산문 부패의
   실증) · `docs/BLUEPRINT.md:1151` ("§5-16") · `docs/DESIGN.md:41·511·518`
   ("§5-11" 등) — **전부 이사 대상 구간을 가리킨다.**
2. 살아있는 문서의 참조는 수술 커밋에서 **함께 갱신**한다 (남는 절 또는 아카이브
   경로로 재지정, 죽은 `.harness/RULES.md` 참조는 CLAUDE.md 안전 규칙 절로).
3. append-only인 `DECISIONS.md`의 HANDOFF 언급 **144건은 고칠 수 없다** → 아카이브가
   원 § 번호를 보존하고, HANDOFF 머리에 "과거 § 번호 구절은 `handoff-archive/`에
   번호 보존 이사됨" 안내 1줄을 남겨 역사적 참조가 계속 해석 가능하게 한다.

**검증 4종 (교체)**: ① 이사 전후 참조 인벤토리 grep 대조 ② 순수 이동 diff(내용
무변경) ③ 새 컨텍스트 복원 시험(§2.10-1 — 채점자는 수술 세션이 아닌 새 컨텍스트)
④ **줄 수 게이트 신설**(HANDOFF ≤500 · RUN-PLAN ≤300, 초과 시 red). ④가 핵심이다 —
"초과 시 이사 의무"를 산문으로 두면 §2.6대로 썩는다는 것을 이 레포가 이미 두 번
실증했다(§3.0 표 ① — D-082(c)의 317KB 진단과 그 대응물의 재비만).

**안전 조치**: 전용 브랜치 + 파일 단위 커밋(중단 시 복구 가능) · 수술 전 `git
fetch` 원격 대조 필수(안전 규칙 R-008 승계 조항 — 3,000줄 재배치가 병렬 머신 편집과
만나면 해소 불가급 충돌).

### 3.3 처방 3 — 판 규약에 재정박 2줄 (§2.7의 적용)

CLAUDE.md 판 실행 규약에 추가: ① "서브에이전트 디스패치 프롬프트에는 해당 작업에
적용되는 안전·행동 규칙 슬라이스를 동봉한다(작업 관련분만, 상한 수십 줄 — §2.7-2)"
② "phase 경계에서 재개점을 미니 갱신한다(2~3줄)".

### 3.4 처방 4 — 승격 규칙 명문화 (§2.6의 적용)

CLAUDE.md에 개정판 규칙을 1줄로: "같은 행동 사고 2회 = 훅 후보 등재, 3회 = 의무
기계화, 파괴적 사고는 1회 즉시 — 기계화안은 오탐·마찰·우회·fail 정책을 갖춰야
한다." 현재 auto-memory에 쌓이는 사고 목록이 그 후보 대장 역할을 한다.

### 3.5 하지 말 것

- **aegis Memory를 이 레포에 활성화하지 않는다** (`.harness/RULES.md` 등 재생성).
  sapkit은 renew 1차에서 `.harness/`를 걷어내고 자기 기관으로 대체했다 — 얹으면 같은
  기관 두 벌(이중 규약)이 된다.
- 기관 신설 금지 — 기관 종류는 완성이다. 문제는 비만·낡음·배선이지 결핍이 아니다.

### 3.6 순서와 검증

착수 순서: **처방 1의 ⓐⓔⓕ(즉효·저위험) → RUN-PLAN 절단(쉬움) → HANDOFF 수술
(어려움, ③④ 문서 조항 포함 한 묶음)**. ⓑⓒⓓ는 후보 대장 등재 상태로 두고 §2.6
요건 도달 시 착수. 각 단계의 검증은 §3.1 공통 요건과 §3.2 검증 4종. 완료 후 효과가
확인되면 그 형태가 §4(aegis)의 템플릿 원형이 된다.

## 4. aegis 적용 설계 (`D:\AI PROJECT\claude-final`)

### 4.0 배치 원칙 (Q2의 답)

**플러그인(claude-final)에 두는 것 = 방법론** — 템플릿·의식(ritual)·범용 검사기.
**각 프로젝트 레포에 두는 것 = 상태** — HANDOFF·결정 로그·큐. 다른 프로젝트의 상태를
claude-final에 모으면 안 되는 이유 4개: ① 커밋 원자성 붕괴(코드와 문서가 딴 레포면
"코드는 판7, 문서는 판6"인 순간이 상시 존재하고 그 드리프트를 잡을 CI도 못 만든다)
② clone 복원성 붕괴("레포 하나로 전부 복원"이 깨지고 두 레포 간 대응은 어디에도
버전 관리되지 않는다) ③ 주입 경로 부재(자동 주입되는 것은 cwd의 CLAUDE.md뿐)
④ 프로젝트 간 혼선·오염. — claude-final의 기존 문서(CHANGELOG·DECISION-GUIDE·
docs/reference)는 **aegis 자신의** 상태 문서로서 정상이며 그대로 둔다.

aegis의 memory 스킬은 이미 이 원칙대로 설계돼 있다(만드는 파일이 전부 대상
프로젝트에 생긴다). 즉 이 설계는 노선 변경이 아니라 **기존 노선의 연장**이다.

### 4.1 현황 대조 — 있는 것과 빠진 것

| 두뇌 기관 | aegis 현재 (v0.35.0) | 판정 |
|---|---|---|
| 사고→규칙 루프 | `memory` Lesson (FAIL→CAUSE→VERIFY→RULE, demote 포함) | **있음** |
| 검증된 사실 축적 | `memory` Knowledge (K-atom, 포인터 원칙 명문화) | **있음** |
| 결정 로그 | `memory` Docs가 대상 프로젝트에 배포하는 `docs/ADR.md` + `docs/reference/decisions/` | **있음** |
| 세션 마감 의식 | `wrap` 6단계 (지식→규칙→문서→유출 점검→커밋 제안→재입선) | **있음** — 단 handoff 갱신이 "프로젝트 규약이 있으면"이라는 조건부 |
| 재개점 핸드오프 | Docs 절의 Handoff discipline (대상 프로젝트의 `docs/reference/handoffs/{topic}.md`, 10KB 초과 경고 포함) | **반쯤** — 규율은 훌륭하나 진입 동선이 약함 |
| **판(run 간) 큐** | 없음 — aegis의 단위는 한 run(INTAKE→…→END) | **빠짐** |
| **세션 시작 복원 의식** | 진입 shim은 구현 라우팅만 — "재개점 읽기 + 원격 대조" 없음. 매처도 `startup\|clear\|compact`로 **`resume` 부재** | **빠짐** |
| **기계 검사층** | 없음 — 문서 규율이 전부 산문 절차 | **빠짐** |

즉 aegis는 "한 판 안"과 "교훈·지식"은 갖췄고, **"판 사이 연속성" 층이 통째로 비어
있다.** 사용자가 겪는 망각이 정확히 그 층이다.

### 4.2 선행 작업: 스펙 개정 (부품보다 먼저)

aegis는 설계서(`docs/reference/designs/2026-08-02-adaptive-aegis.md`)가 단일 정본이고
pytest가 스킬 문언을 리터럴로 고정하며(`assert "..." in text` — 독립 리뷰가 실물
확인) `release_check.py`가 릴리스를 막는다. **스킬 파일부터 고치면 자기 게이트에
걸린다.** 순서: 스펙 개정 → 스킬·훅 구현 → 테스트·release_check 갱신.

**스펙 개정 대상 목록** (리뷰 반영으로 v1보다 확장):

1. "continuity 층" 절 신설 (부품 1~4의 규범).
2. **승인 #4의 열거 확장** — 승인 종류 수(5종)는 늘리지 않되, #4 "Memory 영구
   반영"의 닫힌 열거(`lesson·knowledge·docs·RULES`)에 continuity 산출물(HANDOFF·
   RUN-PLAN)을 추가 개정한다. 문언이 스펙과 DECISION-GUIDE **양쪽**에 있다.
   (v1의 "신규 승인을 만들지 않는다"는 표현은 낙관적이었다 — 열거 자체의 개정이
   필요하며, 이는 "스펙 선행" 결론을 오히려 강화한다.)
3. SessionStart shim의 **payload 예산 규범 갱신** — 현행 4,100B, 실측 2,484B로
   여유 1,616B. 복원 분기는 이 안에서 설계하되 예산 조항 자체가 스펙 §10 규범이다.
4. **임계값 단일화** — memory Docs의 core doc ~300줄·handoff 10KB와 이 설계의
   목표/상한 쌍(300/500 등)을 하나의 규정으로 정리 (§4.7 이중 규약 금지의 임계값판).

### 4.3 부품 1 — continuity 스캐폴드 (옵트인 스킬 또는 memory 6번째 워크플로)

대상 프로젝트에 두 파일을 생성한다. Memory Init과 같은 규칙: **없는 파일만 복사,
기존 파일은 절대 덮지 않음, 생성 결과(created/already_present/failed) 보고.**

**`HANDOFF.md` 템플릿 골격** (루트):

```markdown
# HANDOFF — 상태와 재개 지침
> 목적: 새 세션이 이 문서만 읽고 복원. 상태가 바뀌면 갱신까지가 작업의 일부.
> ⚠ 상한 초과 시 완료 역사를 아카이브로 이사할 것 (검사기가 잰다).

## ▶ 재개점 — 여기부터 읽는다
### 한 문단 요약
### 지금 상태 (표)
### 남은 것 — 부채 목록 (계획이 아님)
### 다음 1~3 (큐 참조)

## 불변 규칙 (또는 CLAUDE.md 해당 절 포인터)
## 머신·환경 메모
```

**`RUN-PLAN.md` 템플릿 골격**:

```markdown
# RUN-PLAN — 판 큐 (다음 할 일의 단일 정본)
| 순번 | 판 | 전제 | 상태(다음/대기/완료→아카이브) |
## 현행 판
## 완료 판 → docs/reference/run-archive/ (포인터만)
```

### 4.4 부품 2 — SessionStart 복원 라우팅

기존 공유 SessionStart 훅(`hooks/`)에 분기 하나: **대상 프로젝트에 `HANDOFF.md`가
존재하면** "재개점부터 읽고, `git fetch` 후 `main..origin/main` 대조로 병렬 줄기
여부를 확인하고 시작하라"를 지시. 없으면 침묵(zero-footprint 유지). "못 찾는" 문제를
끊는 결정적 한 수 — 읽기를 검색이 아니라 의식으로 만든다 (§2.5).

리뷰 반영 3건:

- **매처에 `resume` 추가** — 현행 `startup|clear|compact`에는 재개가 없다. 재개
  세션이야말로 복원 의식이 필요한 자리다.
- **payload 예산 준수** — 분기 추가분은 여유 1,616B 안에서 (§4.2-3).
- **release_check의 측정 사각 수리** — 현행 검사는 `cwd=claude-final`로 훅을
  돌리는데 거기엔 HANDOFF.md가 없어 **분기 채택 경로가 영원히 측정되지 않는다.**
  HANDOFF가 존재하는 픽스처 경로에서도 payload를 재도록 검사를 함께 고친다.

### 4.5 부품 3 — wrap 연결

wrap의 step 3은 이미 "프로젝트가 handoff 파일을 유지하면 커밋 전에 갱신하라"고
말하지만 "규약은 프로젝트 소관"이라며 발을 뺀다. 부품 1이 그 규약의 제공자가 되면:
마감 = 재개점 재작성 + 큐 갱신 + (기존) 유출 점검·커밋 제안·재입선. wrap 문언 수정은
최소로 — continuity 스캐폴드를 handoff 규약의 한 실체로 인식시키는 정도.

### 4.6 부품 4 — 범용 기계 검사 (llm-wiki의 Lint에 해당)

플러그인이 프로젝트 무관하게 제공 가능한 것만:

1. **신선도 검사**: 최근 N커밋이 코드 경로를 만졌는데 `HANDOFF.md` 미갱신이면 경고.
2. **append-only 검사**: 결정 로그(`docs/ADR.md` 등)의 기존 항목 수정·삭제를 거부
   (정정은 새 항목으로). **판정 기준 명시 필수**: 어느 ref 대비인가(병합 기반 대비
   등) — 기준 없이 이력만 보면 rebase·amend·squash에서 대량 오탐이 난다.
3. **링크 검사**: 스캐폴드 문서들의 상대 링크 깨짐 0.
4. **크기 검사**: HANDOFF·RUN-PLAN 상한 초과 시 경고/red (§3.2-검증 ④의 일반화 —
   "이사 의무"는 산문으로 두면 썩는다는 것이 sapkit에서 두 번 실증됐다).
5. **(선택) 고아 문서 검출**: 어디서도 링크되지 않는 콜드 문서 보고 (§2.11).
   **아카이브 디렉터리는 제외** — 아카이브는 의도적 고아(포인터 하나만 남기는 것이
   목적)라서, 제외하지 않으면 검출기와 이사 처방이 서로를 상쇄한다.

제공 형태: 스킬이 안내하는 스크립트 + (선택) 훅. **한계 명시**: sapkit의 기계 생성
대장·provenance 검사 같은 프로젝트 고유 게이트는 배포 불가 — 그 층은 각 프로젝트가
사고를 겪으며 스스로 기른다(§2.9). 플러그인이 주는 것은 §2.6 승격 규칙이라는
"기르는 규율"까지다.

### 4.7 통합 규칙 — 이중 규약 금지 (검토 포인트 ②)

aegis가 **대상 프로젝트에 배포하는** 규약으로 이미 `docs/ADR.md`(결정)와
`docs/reference/handoffs/{topic}.md`(핸드오프)가 있다 (claude-final 자신의 `docs/`에
있는 것이 아니라 memory 스킬이 대상에 만든다 — v1 문구 정정). 여기에 sapkit식
이름(DECISIONS.md · 루트 HANDOFF.md)을 **병렬 추가하면 플러그인 스스로 분기 문제를
만든다.** 하나로 정해서 스펙에 박아야 한다.

권고: 결정은 기존 `ADR.md` 유지, 핸드오프는 **루트 `HANDOFF.md`로 승격**하고 기존
`docs/reference/handoffs/` 규율(크기 상한·승격 규칙)을 그 파일의 유지 규칙으로
흡수. **근거는 "진입 동선"이 아니라** (루트 파일도 자동 주입되지는 않는다 — 리뷰
정정) **"SessionStart 훅이 가리키기 쉬운 단일 고정 주소"**다 — §4.4의 분기가 어느
파일을 볼지 한 곳으로 정해져야 의식이 성립한다. 통합 시 memory SKILL의 Handoff
discipline 문언이 pytest 리터럴 고정에 걸리므로 §4.2 스펙 개정 순서에 포함한다.

### 4.8 검증

pytest 전체 + `release_check.py` green (payload 예산·분기 채택 경로 측정 포함) ·
신규 부품의 음성시험(스캐폴드가 기존 파일을 정말 안 덮는지, 검사기가 위반을 정말
거부하는지, append-only 검사의 rebase 오탐이 정의대로인지) · 실제 프로젝트 1곳
(§5의 아무 프로젝트)에서 새 세션 복원 시험(§2.10-1, 새-컨텍스트 채점자) 통과.

## 5. 일반 프로젝트 적용

### 5.1 지금 (aegis 개조 전) — 수동 최소 세트, 15분

새 프로젝트를 시작할 때 손으로 4파일:

1. **`CLAUDE.md` 10줄** — 정체성 한 문단 + **"세션 시작하면 HANDOFF부터 읽어라"** +
   하지 말 것 2~3개. (자라면 "X 전에 Y를 읽어라" 라우팅과 실패 사례 인라인 추가.)
2. **`HANDOFF.md`** — §4.3 템플릿 골격 그대로 (재개점/상태/부채/다음).
3. **`DECISIONS.md`** — append-only 번호제. 대안을 기각할 때마다 5줄(뭘·왜·뭘 버렸나).
   수정·삭제 금지, 정정도 새 항목.
4. **큐** — 판이 10회를 넘을 것 같을 때만 `RUN-PLAN.md` 분리. 아니면 HANDOFF의 "다음"
   절로 충분.

### 5.2 습관 2 + 성장 규칙 1

- 습관 ①: **세션 끝 = HANDOFF 갱신하고 커밋** (문서 갱신까지가 작업의 일부).
- 습관 ②: **보고에 분모** ("3/10 완료, 미룬 것 2와 이유").
- 성장 규칙: **같은 실수 2회 = 그 문서 자리에 ⚠ 경고 인라인 + 기계화 후보 등재,
  3회 = 검사 스크립트/훅으로 승격, 파괴적 실수는 1회 즉시** (§2.6·§2.9 — 승격 시
  오탐·마찰·우회·fail 정책 포함).

### 5.3 규모별 가감

- **2~3판짜리**: CLAUDE.md + HANDOFF만. 나머지는 과잉이다 (유지비가 이득을 넘는다).
- **10판 이상**: 4파일 전부 + 게이트를 기르기 시작. HANDOFF는 목표/상한 쌍(예:
  300/500줄)을 정하고 **상한은 기계로 잰다** — 산문 "이사 의무"는 sapkit에서 두 번
  실증된 대로 썩는다.
- **기록이 수백 항목 규모**: §2.11 콜드 층 위키화(주제 페이지·교차 링크·고아 검출)를
  연다. 외부 불변 원본을 많이 참고하는 프로젝트는 콜드에 `raw/`+`wiki/` 소구조 허용.

### 5.4 aegis 완성 후

위 수동 세트가 "**플러그인 설치 → continuity 옵트인 승인 → 세션 끝마다 `/wrap`**"으로
대체된다. §4를 만드는 이유가 바로 이 절의 자동화다.

```
sapkit (원형·참조 구현)          aegis (방법론의 배포자)         일반 프로젝트 (수혜자)
```

- **착수 순서는 sapkit 먼저로 확정한다** (v1 검토 포인트 ③에서 내림 — 사용자 결정이

  sapkit 처방이 실증된 형태가 aegis 템플릿의 원형이다.
- sapkit 자신은 aegis의 continuity를 **설치하지 않는다** (자기 기관 보유, §3.5).

## 7. 정직한 한계

1. 기계화 불가능한 판단 실수는 남는다 — 그건 새-컨텍스트 리뷰가 잡는 자리다. 목표는
   망각 0이 아니라 "**나면 잡히고, 잡히면 구조가 된다**".
2. 이 체계에는 유지비가 있다 — 작은 프로젝트에는 §5.3대로 부분집합만. 문서 부기
   (갱신·이사·링크)는 llm-wiki의 통찰대로 세션 마감 의식에서 모델에게 맡긴다.
3. **기계화 자체에도 비용이 있다** (§2.6 정밀화) — 오탐·마찰·오귀인. sapkit에는
   훅을 늘렸다가 되물린 선례(tdd-guard)가 실재한다. 훅은 만능이 아니라 비용면을
   갖춘 안만 승격되는 도구다.
4. 이 문서의 처방은 실측 진단에 기반하나 **아직 미적용·미검증**이다 (§3의 효과는
   적용 후 §2.10 시험으로 확인해야 한다).
5. **v1은 독립 리뷰에서 R-FAIL을 받았고 v2가 그 회수다** — 인용 39건 중 33건이
   일치했음에도 차단 4건(오진 1·자기모순 2·검증 무효 1)이 §3을 재작성시켰다. 이
   문서 자체가 §2.8 완료 정의의 실증이다: 작성 세션의 실측(v1)은 부분 관찰이었고,
   새-컨텍스트 검증이 그 구멍(`.claude/hooks/` 미확인)을 잡았다.
6. 세컨드브레인(qmd류) 인프라는 이식하지 않는다 — llm-wiki 구조의 채택 범위는 §2.11이
   정본이다 (콜드 층 한정, 원본 불변성 기준).
