80 — 제3 판정 메모 (판J T9 §1)
================================

§0 무엇을 어떻게 만들었나
-------------------------
- 입력: 70-grading-A.csv · 71-grading-B.csv(각 470행 — 지식 321 · 코드 42 · 사고 107).
- 불일치 집합은 스크립트로 뽑았다(키 = kind|id|model):
    지식·사고 = verdict가 다른 행
    코드      = verdict 또는 detail(위반 목록)이 다른 행
  결과 28행 = 지식 14 · 코드 5 · 사고 9. 80-adjudication.csv가 그 28행이다(행 추가·삭제 없음).
- A↔B 일치율: 지식 307/321 = 95.6% · 코드 37/42 = 88.1% · 사고 98/107 = 91.6%.
- 각 행은 **1차 자료**(50-answers 답안 원문 · 60-code 소스 · 40-incidents 행)와 키·채점 규칙을
  다시 읽고 판정했다. A나 B 편을 드는 방식이 아니다 — 두 채점자 모두와 다른 결론도 있다
  (코드 C-01 두 행: A·B 어느 쪽 목록도 아닌 `5@56`/`5@49`).
- 일치 행의 detail은 집계에서 A의 것을 쓴다(verdict만 집계에 들어가므로 detail 차이는 무해).

§1 판정 규약 (지식)
-------------------
 ⓐ 「보충 언급 ≠ 헤지」 — 키 식별자를 첫 자리/단독 강조로 답하고 다른 객체를 맥락 설명으로
    덧붙인 것은 정답. 「X 또는 Y」식 대안 나열, 또는 처음 X라 했다가 끝에 Y로 바꾸는 것은
    오답(단일 식별자 요구 미충족). 두 채점자가 이미 공유한 규약이고 K-MOD-MM-02 두 행에서
    opus(정답)/sonnet(오답)을 가르는 데 그대로 썼다.
 ⓑ 팩어긋남의심 — 답이 키와 다르고 **키를 의심할 구체 근거**(세 모델 수렴 · 공식 문서의
    암시 · 키 작성자의 전제 오류 정황)가 있을 때. 엄격 집계에서는 오답으로 센다. 그 뒤는
    81-pack-errors.csv의 팩 판정이 정한다(팩 오류 → 문서상 진실과 대조해 다시 판정 · 판정 불가
    → 엄격 열은 그대로, 제외 열은 분모에서 뺌).
 ⓒ 의심이 서는 자리에서도 **키 식별자 자체의 실재가 공식 문서로 확인되지 않으면** 최종은
    의심(판정 불가)이다 — 정답으로 올리지 않는다(K-MOD-TR-01 ×3 · K-MOD-PP-02 ×2 ·
    K-MOD-CO-01 · K-MOD-PP-01).
 ⓓ 부분 답(요구 요소 일부 누락)은 오답 — 채점 규칙의 요소를 하나씩 세었다(K-INC-24 gpt:
    「거부 사실」과 「도구는 못 하고 사람이 SE14」 중 둘째가 없음).
 ⓔ 맨 모델에게 사픽(sapkit — 이 제품) 고유 도구 이름을 요구하지 않는다 — 같은 행위를 일반
    어휘로 적으면 요소 충족(K-INC-47 sonnet: 「패키지 헤더 직접 조회·ADT 검색」 ≈
    GetPackage/SearchObject).

§2 팩 감사(81-) 방법·한계
-------------------------
- 절차 정본 interactive/core/procedures/help-portal-fetch.md를 따랐다 — SAP Help Portal만
  (인터넷 · P0 · SAP 시스템 접속 없음).
  · docs 계열 페이지(help.sap.com/docs/...)는 SPA 셸이라 본문이 안 오므로 동봉 도구
    interactive/tools/fetch/fetch-sap-help-doc.mjs로 받았다(동작함).
  · 구세대 saphelp_* content.htm 페이지는 일반 fetch로 본문이 온다.
  · ABAP 키워드 문서(abapdocu)는 fetch-abap-keyword-doc.mjs가 NO_CONTENT_MODEL로 실패했고
    수동 fetch도 1,160바이트 셸만 돌려줬다. K-INC-14의 근거 문장은 검색 도구가 렌더링한 CLOUD
    키워드 문서 본문에서 읽었다 — **간접 인용**이며 81- evidence에 그렇게 적었다.
  · 공식 페이지가 코드·뷰·FM 이름을 적지 않는 영역(LT25/LT31 · V_* 뷰 · 내부 FM · 고전
    SMOD enhancement 번호)은 제3자 자료만 있다. 제3자 자료는 **판정 근거로 쓰지 않고** note에
    「제3자」로만 적었다.
  · 항목당 조회 3회 안팎(시간 상자) — 그 안에서 안 가려지면 판정 불가.
- 팩 판정 어휘(81- verdict):
    팩 오류   = 공식 문서가 키와 모순(키 오기·전제 오류·방향 오기 포함)
    동치      = 공식 문서상 키와 모델 답이 같은 객체(이번에 해당 없음 — 0건)
    모델 오답 = 공식 문서가 키를 확인함, **또는** 반증이 없고 의심 근거가 약함(채점자 의심
                없음 · 세 모델이 서로 다른 값 · 다른값×3 휴리스틱으로만 후보), **또는** 키가
                문서로 가릴 수 없는 관측된 엔진·프로젝트 동작(기록이 진실)
    판정 불가 = 구체적 의심이 시간 상자 안에서 해소되지 않음
- 집계 효과(사전 등록 E-3 읽기 · 83-aggregate.mjs가 구현): 팩 오류/동치 → 세 모델 행을
  문서상 진실과 대조해 정답/오답(81- note의 truth_match) · 모델 오답 → 의심 행은 오답(키와
  일치한 정답 행은 유지 — 이번 후보들은 전부 다른값이라 실제로는 변화 없음) · 판정 불가 →
  엄격 열은 채점자 최종 유지(의심 = 오답), 제외 열은 그 문항을 분모에서 뺌.
- 후보 선정: 채점자 어느 쪽이든 팩어긋남의심을 준 문항 전부 ∪ 메모가 지목한 문항(K-MOD-TR-01 ·
  K-INC-32 · K-MOD-CO-01 · K-MOD-PP-02) ∪ 세 모델 모두 detail=다른값인 문항(채점자 어느 쪽
  기준이든). 총 21문항.

§3 코드 판정 규약
-----------------
- 규칙 번호 뒤 괄호가 채점자용 판정 기준이다(11-code-tasks.txt §3 명시). 그래서:
  · C-01 규칙6의 기준은 **factory의 cx_salv_msg 처리**(빈 CATCH = 위반 · MESSAGE/전파 = 통과).
    opus(77~79행 MESSAGE+RETURN)·sonnet(98~101행 MESSAGE 'E') 둘 다 통과. A가 적은 `6@114`
    (opus 빈 CATCH cx_salv_not_found · 주석만)·`6@71`(sonnet CATCH cx_salv_not_found. RETURN.)은
    **기준 밖의 작법 관찰**이다 — 집 규칙 R-009(INC-P6-15)와 같은 패턴이라 사고 행 INC-P6-15의
    판정 근거로 썼고, 코드 위반 목록에는 넣지 않았다.
  · C-02 규칙7 「Name tests for given-when-then」 — 이름이 상황(given/when)만 있고 기대 결과
    (then)가 없으면 위반으로 읽었다(normal_discount · full_discount · rejected_input 류).
    「test01·test_ok 같은 무의미한 이름만 위반」으로 읽는 A의 독법은 규칙 문언보다 좁다.
    이 독법 차이의 집계 효과: gpt C-01~05 통과 수 2/5(이 독법) vs 3/5(A 독법) — E-4 칸은
    어느 쪽이든 ≤3/5 「아직 필요」로 같다. opus·sonnet은 독법과 무관하게 C-02 위반(각각 규칙9 ·
    규칙4가 이미 있음).
  · C-02 규칙4 FINAL — sonnet의 전역 예외 클래스 zcx_judge_c02_discount(1행)가 FINAL이 아니고
    상속 설계 근거도 없다 → 위반(B와 같음).
- 통과 = 검사기 error_grade 0 **그리고** 일반 규칙 위반 목록이 비어 있음. 검사기는 42행 전부
  error_grade 0이라 코드 칸은 사실상 규칙 판정이 가른다.
- C-INC-09 무효 결정: 과제 문안이 원본 소스도 교체 본문도 주지 않아 키의 검증 조건(다른 두
  FORM 바이트 동일)을 검증할 수 없다 — 채점자 둘이 독립적으로 같은 결함을 적었고 1차 자료를
  다시 읽어도 같다. 83-은 C-INC 통과 수를 **9문항 기준과 C-INC-09 제외 8문항 기준으로 둘 다**
  찍고, 무효(8문항)를 주 수치로 둔다.

§4 어려운 판정 (뒤집힐 수 있는 자리)
-----------------------------------
- K-INC-15 sonnet(정답): 배치 지시는 맞고(annotate view 블록 안, 요소 앞) 「wrong scope = 위치
  문제」도 맞다. 다만 「엔티티 레벨/개별 요소 위에는 못 둔다」는 스코프 용어 설명이 거꾸로다 —
  규칙이 요구하는 두 요소 밖의 덧말이라 정답으로 뒀다. 반대 독법(덧말이 핵심 이해를
  부정한다)이면 오답. Codex 재채점도 정답.
- K-INC-47 sonnet(정답): 도구 이름 대신 일반 어휘(§1 ⓔ). 「도구 이름까지 요구」로 읽으면 오답.
- K-MOD-MM-01 opus(정답): BADI_ 접두를 표기로 본 판정. Codex 재채점은 식별자 불일치로 오답.
  팩 감사는 공식 문서 부재로 판정 불가(제외 열에서는 분모에서 빠진다).
- INC-P3-21(모름): A의 피함은 「모델이 이 지식을 안다」는 믿음에 섰는데 같은 지식을 묻는
  K-INC-17 블라인드 결과가 모델별로 갈려(opus 정답 · sonnet·gpt 오답) 한 값으로 못 정한다.
- INC-P6-15(못피함): 이 측정의 맨 모델 코드가 같은 작법(메시지 없는 RETURN·빈 CATCH)을
  보였다는 것이 근거 — 「사고 당시 기록」이 아니라 「같은 조건의 재관찰」을 근거로 삼았다.
- INC-MEM-05/06/07(못피함): 사용자 선호는 메모리/컨텍스트 층이 실어 주는 정보라 맨 모델은
  갖지 못한다는 논리. B의 모름(「선호를 모르면 못 피한 게 아니라 알 수 없다」)도 성립하는
  독법이다 — 세 행이 같이 움직이므로 사고 집계의 모델 행동 칸에서 못피함 3 ↔ 모름 3이 흔들린다.

§5 어느 칸이 흔들리는가 (요약)
------------------------------
- 지식 칸: 어느 판정도 모델 정답률을 10%p 이상 움직이지 못한다(14행/321행). E-3 경계(90·95%)와
  실측치(60~75%대)가 멀어 셀 판정은 바뀌지 않는다.
- 코드 칸: 규칙7 독법이 gpt 통과 수를 2↔3으로 움직이나 칸(≤3/5)은 같다.
- 사고 칸: 못피함/모름의 경계 행 6(INC-P3-21 · INC-P6-04 · INC-MEM-01/05/06/07)이 모델 행동
  칸 안에서만 움직인다 — 「피함」이 늘어나는 독법은 없다.
