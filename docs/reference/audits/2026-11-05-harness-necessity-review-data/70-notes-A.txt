1. 채점 규약 (계약을 어떻게 적용했는가)
====================================================================
[지식]
- 정답 = grading_rule의 '+'로 묶인 요구 요소를 전부 담았을 때. 하나라도 빠지면 오답(detail=부분).
- 단일 답에 "~로 기억한다/~일 것이다" 식의 보류 표현이 붙은 것은 정답으로 본다(답은 하나다).
- 둘 이상을 나란히 "X 또는 Y"로 내면 오답. 규칙이 복수 후보를 허용한 항목은 없었다.
- 다른 해석을 위한 각주식 부기("만약 ~를 묻는 것이면 ~")는 보류로 보지 않는다 — 본답이 하나로 서 있으면 본답만 본다.
- 규칙 밖의 덧말이 틀려도 판정을 바꾸지 않는다. 단, 요구 사실과 모순되는 덧말이면 오답.
- detail: 요구 요소 일부만 있으면 부분 · 키와 다른 식별자/주장이면 다른값 · 답을 내지 않거나 모른다고 하면 무응답.
- 답변 언어(한/영)는 무관.
- 팩어긋남의심은 "키보다 모델 답이 실제 SAP에 맞을 가능성이 있다"고 내가 보는 경우에만 썼다(11문항 21행). 키는 손대지 않았다.

[코드 C-01~C-05]

- 번호 규칙 목록에 없는 일반 작법(예: C-01의 주석 배너)도 세지 않았다 — 계약이 "번호 규칙"이라서다.
- SELECT ... INTO TABLE 직후 대상 테이블 IS INITIAL 검사는 sy-subrc 검사와 동등으로 인정했다.
- 판단이 갈릴 수 있는 적용 셋: ⓐ C-01 규칙6 — CATCH cx_salv_not_found를 빈 블록(주석만)·RETURN만으로 끝낸 것을 「오류를 삼킴」으로 셌다(Opus 6@114 · Sonnet 6@71). ⓑ C-02 규칙4 — 예외 클래스를 FINAL로 두지 않은 것을 셌다(Sonnet 4@1 · 상속 설계 근거 없음). ⓒ C-02 규칙5 — public 시그니처에 쓰인 public TYPES는 세지 않았다. ⓓ C-02 규칙7(given-when-then 이름)은 무의미한 이름만 세는 쪽으로 느슨하게 적용 — 해당 없음.
