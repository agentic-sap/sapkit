# 하네스 필요성 검토 — 모델이 좋아진 지금, sapkit의 어느 층이 과한가

> 작성일: 2026-11-06 (측정 착수 2026-11-05)
> 상태: **측정·판정 완료 / 리뷰 회수 전 — 처방은 문서뿐이고 집행은 0**
> 실행 분류: **Direct / P0 offline**

이 문서는 판J(판 — 결정 · 준비 · 실행 · 리뷰로 도는 이 레포의 작업 한 사이클 · 착수 결정 [D-156](../DECISIONS.md))의
감사 문서다. sapkit의 층마다 「지금 모델 기준으로 여전히 값을 하는가」를 오프라인 측정(SAP에 접속하지 않는 측정)으로
재고, 층마다 처방을 적었다. **처방은 문서일 뿐이다** — 이 판은 제품 파일을 하나도 고치지 않았고, 걷어내는 집행은
별도 판이 한다. 과거 소유자 결정과 어긋나는 처방은 **권고**로만 적었고, 고르는 것은 소유자다(완료 항목 D-157).

원자료는 전부 자료 폴더([README.txt](2026-11-05-harness-necessity-review-data/README.txt))에 있다. 이 문서의
수치는 그 파일들에서 옮겼고, 옮긴 자리마다 「파일 번호 §절」로 출처를 붙였다 — 예를 들어 `83 §3`은
[83-results.txt](2026-11-05-harness-necessity-review-data/83-results.txt)의 3절이고, `83 §7 · §8`처럼 파일 번호
뒤에 이어 쓴 §도 같은 파일의 절이다. 파일 번호 없이 「§7」처럼만 쓰면 이 문서의 절이다.

## 0. 한 문장 결론

**모델이 혼자서 이미 아는 것은 나라·업종별 기본 사실 정도이고, 업무 모듈 지식과 ABAP(SAP의 프로그래밍 언어)
코드를 규칙대로 짜는 일은 아직 하네스(모델 둘레에 붙인 지식·절차·규칙 묶음)가 채워 줘야 한다 — 과한 곳은
지식이 아니라 절차가 한 번에 읽어 들이는 분량, 사람에게 묻는 질문 수, MCP(모델이 SAP를 부르는 도구 연결)
도구 설명의 길이다.**

| 층 묶음 | 처방 | 한 줄 이유 |
|---|---|---|
| 지식 — 모듈 · ABAP 작법 · 페르소나 · 집 규칙 | **유지** | 맨 모델(지식 없이 기억만으로 답한 모델)의 모듈 정답률 56.7~63.3% · 코드 5과제 중 2과제 통과 — 아직 모른다. 집 규칙(이 작업장의 취향)은 재지 않고 둔다 |
| 지식 — 나라·업종의 「사실」 부분 | **제거 후보** (집행 전 재측정) | 세 모델 모두 16/16 · 7/7, 비싼 항목(틀리면 비용이 큰 세법 · 국가 규정 같은 문항) 오답 0 — 단 나라당 1문항 · 1회 응시 |
| 절차의 질문 · 절차 1회 적재 · MCP 도구 설명 | **축소** | 질문의 31.6~57.1%는 모델이 스스로 찾을 수 있다 · 절차 한 번에 30,747~157,482 토큰(모델이 읽는 글자 묶음 — 비용 단위 · 바이트÷4 근사) · 도구 하나 설명에 841~910바이트 |
| 정책 · 절차의 행동 규범 · 수정과 이송 절차 · 서버 게이트 · 표면 프리셋 · 리뷰 · 검사기 · 훅 · 연속성 · 3사 구조 · 공방(이 레포를 만드는 쪽의 개발 장치)의 게이트 · 기록 · 판 체제 · 공방 훅 | **유지** | 끌 수 없는 안전 장치를 품었거나, 실제로 막은 사고가 있거나(리뷰 루프 6건), 세션 비용이 거의 0이거나, 줄일 질문이 없다(수정 · 이송 절차의 유도 가능 0%) — 층마다의 근거는 §4 |
| 나라·업종의 커스터마이징 · 함정 같은 절 · 세션 고정 분량(제품 · 공방) | **측정 후 결정** | 시험이 그 절에서 문항을 뽑지 않았다 · 세션 고정 분량은 둘 다 미리 정한 두 선 사이(제품 3,242 — 3k~8k · 공방 19,463 — 10k~20k) |

**가설과 나란히**(§7.5) — 맞은 곳: 과한 이유는 모델의 SAP 지식 향상이 아니라 절차 · 질문 · 도구 설명의 두께다.
어긋난 곳: 나라·업종의 기본 사실은 세 모델이 이미 안다 — 이 좁은 칸에서는 지식 향상이 실제 이유다. 「늘 실리는
무게는 도구 설명」은 도구 설명을 처음부터 싣는 하네스에서만 맞다.

## 1. 질문 · 전제 · 가설

### 1.1 사용자 원문

> 지금 모델들이 좋아지면서 SAP도 학습이 많이되서 모델자체만으로도 MCP연결해서든 뭐든 개발을 충분히
> 잘하는거같아. 그래서 이 프로젝트의 하네스가 좀 과하지 않은가 생각되는데 어떤지 검토해줘.

### 1.2 「과하다」를 무엇으로 재나

과함 = 비용이 값보다 크다.

| 쪽 | 무엇 |
|---|---|
| 비용 | 토큰 — 세션 고정(대화를 열 때마다 늘 실리는 분량)과 호출 시 적재(그 기능을 부를 때 읽히는 분량) · 사람 시간 — 질문 · 승인 · 멈추는 자리 · 리뷰 왕복 |
| 값 | 증거 — 모델이 모르는 지식을 채웠는가 · 사고를 막았는가 · 막을 수 있었는가 |

### 1.3 기준선 — 「모델 혼자」란

- **기준선** = 같은 모델 + sapkit의 MCP 서버 그대로. 지식 · 페르소나 · 절차 · 정책 · 훅 · 리뷰 루프 · 연속성
  층은 없이. 사용자 원문의 「MCP연결해서든」을 그대로 옮긴 것이다.
- **「뭐든」의 범위** — 사용자 말은 MCP 없는 길도 담는다(abapGit — ABAP 소스를 파일로 주고받는 도구 — 으로
  반입하거나 Eclipse에서 직접 개발). 그 길은 따로 재지 않았고, 측정은 위 기준선으로 했다.
- ⚠ **실제 응시 조건은 기준선보다 더 맨손이었다** — 지식 시험과 코드 시험은 도구 0개(MCP도 없이)로 치렀다.
  그래서 「모델이 MCP로 SAP를 찾아보며 푸는 실력」은 이 판이 재지 않았다(§7.8 · §6의 「실제 비교 1회」).
- **L5(MCP 서버) 자체의 기준선** = 모델 + 범용 ADT MCP 서버(ADT — SAP의 개발 도구 인터페이스). 그 서버의 소스를
  실행하지 않고 도구 등록점만 읽어 대조했다([20-tokens.txt](2026-11-05-harness-necessity-review-data/20-tokens.txt) §7 · 이 문서 §3.8).

### 1.4 기준 모델

| 모델 | ID | 왜 |
|---|---|---|
| Claude Opus 5.5 | `claude-opus-5-5` | 소유자가 주로 쓰는 모델 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | 약한 모델 대표 |
| Codex | `gpt-5.6-sol` | 다른 회사 하네스 대표(sapkit은 3사 중립이다) — 응시 때 추론 설정 medium |

Antigravity 쪽 모델은 응시하지 않았다(D-156 정직 유보 ⑺).

### 1.5 가설 — 검증 대상이지 결론이 아니다

> 과한 곳은 있으나, 그 이유는 모델의 SAP 지식 향상이 아니라 절차·공방의 두께일 공산이 크다. 늘 실리는 무게는
> MCP 도구 설명이고 그것은 모델 혼자 MCP를 붙여도 똑같이 든다.

착수 때 설계자가 판 준비 문서(레포에 커밋되지 않는다)에 적은 잠정 판정이다. 레포에 남은 원문은 첫 문장의
요지 — D-156 정직 유보 ⑸ 「과한 곳은 있으나 이유는 절차·공방의 두께이지 모델의 SAP 지식 향상이 아닐 것」 — 이고,
결과와의 대조는 §0과 §7.5에 있다.
공방(이 레포를 만드는 쪽의 개발 장치 — 제품 사용자에게는 가지 않는다)은 §5에서 따로 본다.

### 1.6 소유자가 정한 것 (D-156 「소유자 결정 열」)

| | 정한 것 |
|---|---|
| ⓐ | 대상 = 제품 전체 + 공방 부록 |
| ⓑ | 증거 = 오프라인 측정 — 실 SAP A/B는 다음 판 후보로 남긴다 |
| ⓒ | 과거 소유자 결정도 재심 — 안전 규칙 셋만 뺀다 |
| ⓓ | 결과물 = 판정 + 층별 처방 + 다음 판 후보 · 집행은 별판 |
| ⓔ | 척도 = 토큰과 사람 시간 둘 다 |
| ⓕ | 코드 시험을 넣고, ABAP 규약은 집 규칙(이 작업장이 정한 취향)과 일반 작법(어느 SAP 현장에서나 통하는 작법)으로 가른다 |
| ⓖ | 통과선 = 전체 95% + 비싼 항목 오답 0 |
| ⓗ | 기준 모델 = Opus 5.5 + Sonnet 5.5 둘 다 |

**재심에서 뺀 안전 규칙 셋** — 실데이터 추출은 건별 사람 승인(P2) · 쓰기는 DEV(개발 시스템)에서만 · 이송(P4 —
개발 결과를 다른 시스템으로 옮기는 SAP 절차)은 사람 소유. P0~P4는 SAP 정책 등급이다(P0 오프라인 · P1 접속 읽기 ·
P2 실데이터 추출 · P3 쓰기·실행 · P4 이송). 공방 안전 규칙 나머지 다섯(동결 원본 무접촉과 private 금독 · 비밀정보 ·
번들 보호 · SAP 접점 이원화 금지 · 재개 전 원격 대조)도 재심 밖이다. 안전 규칙 가운데 「write 성공 보고를 그대로
믿지 않는다」(쓴 뒤 소스를 되읽어 확인)는 이 목록에 없다 — 그래서 재심 대상으로 다뤘고, 검증 정책(L4-b)과 리뷰
루프(L8) 행에서 판정했다.

### 2.3 처방 규칙

- **처방 어휘 다섯** — `유지` · `축소`(남기되 얇게 — 설명문 · 질문 · 분량 줄이기) · `스위치화`(끌 수 있게 — 방향을
  적는다) · `제거` · `측정 후 결정`(이 판의 증거로는 못 정함 — 다음 판 후보로).
- **두 모델 규칙(선 ⑸)** — 전제가 적용되고 시험이 있는 층에만 쓴다.

| 시험 결과 | 처방 |
|---|---|
| Opus ✗ | 유지 |
| Opus ✓ · Sonnet ✗ | 스위치화(기본 켜짐) |
| Opus ✓ · Sonnet ✓ | 제거 후보(제거 불가 · 집 규칙 제외 · 적용 대상 = 모든 사용자 기본값 · 집행은 별판) |
| Claude 둘 다 ✓ · Codex ✗ | 스위치화(3사 중립이라 다른 회사 모델도 사용자다) |
| 선 근처 | 측정 후 결정 |

- **시험이 없는 층**(전제 「아니오」) — 토큰 · 사람 시간 · 사고 증거로 판정한다. 「전제와 무관」을 숨기지 않는다.
- **사고로만 재는 층**(절차의 모델 행동 규범 · 리뷰 루프) — 전제는 「예」지만 모델별 시험이 없다. 두 모델 규칙을
  쓰지 않고 사고 집계와 토큰 · 시간으로 판정한다. Opus · Sonnet 칸은 「해당 없음」.
- **제거 불가** — 재심에서 뺀 안전 규칙 셋의 유일한 집행 지점(서버 tier 게이트 · 테이블 blocklist · 리뷰어
  `disallowedTools`(리뷰어가 쓰지 못하는 도구 목록) · 승인 관문의 P2 부분 · `release`의 승인 규칙). 처방은 유지 · 축소 ·
  스위치화 중에서만.
- **집 규칙**(이름 · 인클루드 구조 · 상수 · 텍스트 요소 · OK 코드 · OOP 배치 · abapGit 왕복 · 소스 수리 · 템플릿) — 어떤
  모델도 맞힐 수 없는 취향이라 측정 없이 유지(선호).
- **과거 소유자 결정과 어긋나면** — 표에 D-번호를 적고 **권고**로 둔다.
- **선을 쓸 수 없는 자리만** 측정 후 결정 — 왜 쓸 수 없는지 적는다(§7.7).

### 2.5 채점과 일치율

1. **채점자 A · B** — 독립 두 채점(지식 321행 · 코드 42행 · 사고 107행).
2. **제3 판정** — 둘이 갈린 28행(지식 14 · 코드 5 · 사고 9)을 1차 자료로 다시 판정(80 §0).

   채점 쪽 일이라 공식 도움말 사이트를 직접 읽었다(SAP 시스템 접속은 없음). 문항당 조회 3회 안팎의 시간 상자 ·

## 4. 층별 판정표

### 4.1 읽는 법

- 표는 둘이다 — 「무엇을 쟀나」(증거)와 「그래서 어떻게 하나」(처방). 같은 ID가 두 표에 같은 순서로 있다.
- **토큰 칸**은 ÷4 값이다(2026-11-05 측정값). **사고 칸**은 「막음 · 막았을 · 켜져 못 막음(자기 자리) · 불명」이다
  (83 §8). **시험 칸**은 Opus / Sonnet / Codex 순이다.
- **처방 칸**은 다섯 어휘 중 하나로 시작한다. 괄호 안은 방향 · 조건이다.
- **적용 대상**은 모든 사용자 기본값 / 스위치 / 소유자 설정 중 하나다. **제거 불가**는 예 · 부분 · — 중 하나다.
- 규칙 결과와 작성자 판단이 갈린 자리는 처방 칸을 규칙대로 두고 근거 칸과 §7.6에 적었다.

## 7. 정직 유보

### 7.1 근사

- 토큰 판정은 ÷4다. 한국어 위주 문서는 ÷4가 토크나이저보다 1.6배쯤 낮게 잡힌다(CLAUDE.md 1.60 · HANDOFF.md
  1.68 · 공방 셀 1.61). 영문 JSON · 산문은 0.87~1.01로 ÷4가 맞는 편이다(20 §5).
- 토크나이저는 OpenAI 계열 대용이다 — Claude 토크나이저는 로컬에 없다. 비율은 방향만 읽는다.
- 스킬 · 에이전트의 「호스트 렌더」는 측정 세션에서 본 형식을 재구성한 추정이다(20 §8).
- 1-hop은 정적 상한이고, 접속 표면은 재지 않았다(§3.1).

### 7.2 표본 1회 · 작은 표본

- 문항마다 1회 응시다 — 같은 질문을 다시 물으면 답이 달라질 수 있다. 재현성은 재지 않았다(83 §11).
- 범주 표본이 작다(나라 16 · 업종 7 · ABAP 7) — 한 문항이 범주 판정을 뒤집는다. 나라 16/16에서 한 문항만
  틀렸어도 93.8%로 「측정 후 결정」이 됐다.
- 참고 계산(작성자) — 정답률이 실제로 83% 정도인 모델도 16문항을 모두 맞힐 확률이 5%쯤 있고, 7문항이면 실제
  65% 정도인 모델도 그렇다. 세 모델이 함께 다 맞힌 것은 그보다 강한 신호지만, 세 모델의 실수는 서로 독립이
  아닐 수 있다. 그래서 L1-b · L1-d의 「제거」는 §6 ② 재측정 뒤에만 집행한다.
- 나라는 나라당 1문항이고, 업종은 14개 중 7개만 표본에 들었다. 코드는 5과제다.

### 7.3 검사기는 뜻을 보지 못한다

- 검사기는 문법 · 작법만 보고 업무 뜻이 맞는지는 못 본다(D-156 정직 유보 ⑶).
- `parse`는 토크나이저다 — 오류급 0은 「검사기가 닿는 범위에서 0」이지 「SAP에서 활성화된다」가 아니다(83 §11).
- C-INC-06에서 활성화를 깨는 구조(이벤트 블록 뒤의 선언)를 검사기가 잡지 못했다(§3.4). 일반 작법 위반은 전부
  채점자가 봤다.

### 7.4 사고 증거가 약한 곳

- 그때 켜진 층을 기록이 적지 않은 사고가 54/163이다. L1은 막았을 45건 중 33건이 켜짐 불명이다.
- 「막았을」은 사고를 분류할 때 적은 반사실 판단이고, 비재현 판정은 기록 문장만 읽은 판정이다(83 §11).
- SAP · 엔진 성질 48행은 전부 「못 피함」이다 — 원인이 모델 밖이라는 뜻이지 모델 실력을 말하지 않는다(§3.5).
- 어떤 층으로도 못 막았을 사고가 23/163이다.
- 채점이 흔들릴 수 있는 사고 행이 있다 — 사용자 선호를 몰라 생긴 세 행(INC-MEM-05 · 06 · 07)은 「못 피함」과
  「모름」 사이에서 함께 움직인다. 「피함」이 늘어나는 읽기는 없다(80 §4 · §5).

### 7.7 선을 쓸 수 없었던 자리 · 선의 읽기

- **L1-c · L1-e** — 표본기가 그 절에서 문항을 뽑지 않아 선을 댈 값이 없다 → 측정 후 결정.
- **「또는」 읽기** — 선 ⑴의 「90~95% 또는 비싼 항목 오답 1」을 집계는 「90% 미만인데 비싼 오답이 1이면 아직 필요」로
  읽었다. 문자 그대로면 「측정 후 결정」이다. 이 읽기에 걸린 칸은 주 판정 15칸 중 0칸이고, 민감도 줄 2개(Sonnet ·
  Codex)뿐이다(83 §2).
- **S2 · W1** — 선 사이라 선이 정한 대로 측정 후 결정이다. 선을 옮기지 않았다.
- **W4(판 체제)** — 공방의 사람 시간 · 벽시계에는 사전 등록된 선이 없다. 사고와 기록으로만 판정했다.

### 7.8 모델별 유보

- **Opus 5.5** — 응시자이면서 집계 스크립트와 이 문서의 작성자다(§2.7). 판정 칸은 기계적으로 옮겼지만 처방 칸의
  판단(L1 나누기 · L1-f 척도 고르기)은 작성자가 했다. 판 마감 전 마지막 독립 리뷰도 Opus 5.5 새 컨텍스트로
  예정돼 있어 비응시 모델의 리뷰가 아니다.
- **채점자** — 셋(A · B · 제3)이 한 계열(Claude Fable 5.1)이다. 계열 편향은 Codex 재채점 43행 1회로만 가늠했다
  (83.7%).
- **Codex** — 응시 추론 설정이 medium이다(재채점은 high). 응시 도중 계정 한도로 기다렸다가 이어 갔다(표본 손실 0).
  읽기 전용 셸 도구가 남았으나 도구 호출 0으로 확인했다.
- **Sonnet** — 약한 모델 대표로서 모듈 56.7%로 가장 낮았다. 다른 칸은 Opus와 거의 같았다.
- **공통** — 모델 ID는 CLI가 보고한 값이다. 서버 쪽 실제 가중치 판은 확인할 수 없다. 지식 · 코드 시험은 MCP 없이
  치렀으므로 「MCP를 붙인 맨 모델」의 실력은 이 판의 결과에 없다(§6 ①). Antigravity 모델은 응시하지 않았다.
