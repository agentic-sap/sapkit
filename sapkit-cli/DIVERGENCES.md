# DIVERGENCES — 구 vsp 검사기와 sapkit 검사기의 의도적 차이 (append-only)

이 장부는 **사람용 근거 기록**이다. 규율은 엔진(`harness/DIVERGENCES.md`)과 같다:

- **등재되지 않은 차이는 결함이다.** 코퍼스 대조에서 갈림이 나오면 어느 쪽이 옳은지
  근거를 남기고, 기준 파일이나 코드 중 옳은 쪽으로 수렴시킨 뒤 여기에 적는다.
- **append-only.** 기존 항목을 고치거나 지우지 않는다. 정정도 새 항목으로 단다.
- **비커밋 코퍼스(vsp 내장 샘플)에서 난 갈림은 원본 경로·코드를 적지 않는다** —
  갈림을 재현하는 **최소 합성 조각**으로 치환해 기재한다(공개 레포 유출 차단).
- 항목은 아래 형식을 지킨다. 병합 충돌은 항목 단위로 푼다.

## D-001 — 비-UTF-8 원문의 바이트를 그대로 나르지 않는다 (열이 밀린다)

- **표면**: parse (행·열을 싣는 lint·analyze에도 그대로 전파)
- **구 vsp**: 입력이 바이트열이라 유효하지 않은 UTF-8 바이트도 **그대로 흘러간다**.
  그 바이트는 토큰 문자열에 원래 값으로 남고 **열을 1칸** 차지한다.
- **sapkit**: 입력이 문자열이다. 파일을 읽는 순간(`utf8`) 그런 바이트는 이미
  U+FFFD로 바뀌어 있고, U+FFFD는 UTF-8로 3바이트라 **열을 3칸** 차지한다.
- **재현 (최소 합성 조각)**: Latin-1로 저장된 `WRITE 'ü'.` — 바이트
  `57 52 49 54 45 20 27 FC 27 2E`. 마침표의 열이 구 10, 새 12.
  `DATA lv_ä TYPE i.`(바이트 `E4`)에서는 `TYPE`이 구 11, 새 13.
  실측 4건 중 3건이 갈렸고, **문장 유형은 세 건 모두 같았다**(갈리는 것은 열뿐).
- **왜**: 바이트를 그대로 나르려면 코어 표면이 문자열이 아니라 `Buffer`를 받아야
  하고, 그러면 규칙·CLI 표면 전체가 함께 바뀐다. 이 부품의 설계 전제는
  "런타임 외부 의존 0 · 표준 문자열 표면"이므로 표면을 지키고 차이를 등재한다.
  덧붙여 구 구현도 그 바이트를 **글자로 이해한 것이 아니라 흘려보냈을 뿐**이다 —
  Latin-1 원문에서는 두 구현 모두 글자 단위 열을 주지 못한다.
- **닿는 범위**: SAP 내보내기가 Latin-1/CP1252인 경우에만 나타난다. 레포 안의
  `.abap` 163파일은 전부 유효한 UTF-8이라 코퍼스 대조에서는 드러나지 않는다.
- **판정**: 의도적 차이

## D-002 — analyze 표면의 `local_variable_names`는 등록만 되고 아무것도 하지 않는다

- **표면**: analyze
- **구 vsp**: `allRules()`가 이름 무늬를 하나도 주지 않은 채 이 규칙을 등록한다. 무늬를
  컴파일하는 자리가 빈 문자열을 「없음」으로 돌려주므로 세 종류(변수·상수·필드 심볼)가
  전부 검사 대상에서 빠지고, **한 건도 나오지 않는다**(코퍼스 47파일 실측 0건). 그런데도
  결과의 `rulesApplied`는 등록 수 그대로 **13**이다.
- **sapkit**: 같다. `analyzeRules()`가 무늬 없이 이 규칙을 등록하고, 무늬가 빈 종류는
  검사에 넣지 않는다. `rules_applied`도 13으로 낸다.
- **재현 (최소 합성 조각)**: 메서드 본문의 `DATA counter TYPE i.` — lint 표면에서는
  울리고 analyze 표면에서는 조용하다. 그래서 analyze는 「규칙 13종을 적용했다」고
  보고하면서 실제로 발견을 낼 수 있는 규칙이 **12종**이다.
- **왜**: 이 판의 완료 기준은 **판정 동등성**이다(spec §2.2·§8). 무늬를 채워 넣으면
  analyze 판정이 늘어나 기준 채록본과 즉시 갈린다. 고치는 것은 「승계 뒤에 무엇을
  바로잡을까」를 따로 정하는 후속 판의 일이고, 그때는 이 항목에 새 항목으로 정정을 단다.
- **판정**: 알려진 무동작 승계

## D-003 — SAP에서 소스를 가져오는 길을 승계하지 않는다 (세 곳)

- **표면**: lint · parse · analyze
- **구 vsp**: 로컬 파일 말고도 **SAP에서 소스를 끌어오는 입구**가 셋 있었다.
  ① `vsp lint <TYPE> <NAME>` — `--file`/`--stdin`이 없으면 접속해 `GetSource`.
  ② `vsp parse <TYPE> <NAME>` — 같은 되돌림.
  ③ `AnalyzeABAPCode`는 `source`가 비고 `object_name`이 있으면 30초 타임아웃으로
  `GetSource`를 부른 뒤 그 결과를 분석했다(`codeanalysis.go` `AnalyzeABAPCode`).
  게다가 analyze는 **MCP 도구**였다 — 부르려면 서버를 띄워야 했다.
- **sapkit**: 셋 다 없다. 입력은 **파일 · 디렉터리 · 표준입력뿐**이고, 파일은
  `--file`이 아니라 **위치 인자**로 받는다(`sapkit lint <file>`). 그래서 `<TYPE> <NAME>`
  자리 자체가 사라졌고, 위치 인자를 둘 주면 사용 오류다. analyze는 MCP 도구가 아니라
  보통 명령이며 **SAP 접속·MCP 서버 모드를 만들 길이 코드에 없다.**
- **곁딸린 것**: 구 결과의 `objectUri`·`objectName`은 SAP에서 가져온 객체를 가리키는
  라벨이라 채울 값이 없다. 구 구현도 비면 빼고 냈으므로(`omitempty`) source만 준
  호출과 결과가 같다 — 두 키가 결과에 나타나지 않는다.
- **왜**: spec §2가 「SAP 접속 없음 · MCP 모드 없음 · 입력은 파일/디렉터리/표준입력뿐」을
  공통 전제로 못 박았고, 이 판의 절대 관문 ①도 같은 말이다. 오프라인 검사기에 접속
  경로를 남겨 두면 그 전제가 코드 한 줄로 무너진다.
- **판정**: 의도적 차이

## D-004 — 구 `--stdin`의 Windows 미작동을 승계하지 않는다

- **표면**: lint · parse (analyze는 구 CLI에 `--stdin`이 없었다)
- **구 vsp**: `readStdin()`이 `os.ReadFile("/dev/stdin")`이다(`cli_extra.go`). Windows에는
  그런 경로가 없어 열기부터 실패한다. `lint`는 그 오류를 물고 죽지만(exit 1),
  **`parse`는 오류를 버린다**(`data, _ := readStdin()`) — 빈 소스를 파싱한 `[]`를
  **exit 0으로** 돌려준다. 조용히 틀린 답이라 부른 쪽이 알아챌 방법이 없다.
- **sapkit**: `--stdin`은 fd 0을 그대로 읽는다(`readFileSync(0, 'utf8')`). 플랫폼을
  가리지 않고, 못 읽으면 **입력 오류로 비-0**이다 — 빈 결과를 0으로 내는 길이 없다.
  표준입력에 붙는 이름은 `<stdin>`으로 통일했다(구는 lint `stdin.abap` · parse `stdin`).
- **왜**: spec §2가 세 표면 모두에 `--stdin`을 명시한다. 이건 **판정을 조이는 것이
  아니라 플랫폼 결함을 고치는 것**이다 — 같은 소스를 파일로 주든 파이프로 주든 판정은
  같다. 그래도 관측 가능한 차이이므로 등재한다.
- **판정**: 의도적 차이

## D-005 — 구 `parse --format json`의 이스케이프 결함을 승계하지 않는다

- **표면**: parse
- **구 vsp**: JSON을 직렬화기 없이 **손으로 이어 붙인다** —
  `fmt.Printf("{\"type\":\"%s\",\"tokens\":[\"%s\"]}", s.Type, strings.Join(toks, "\",\""))`
  (`cli_compile.go` `runParse`). 토큰 문자열에 `"`가 하나라도 들어가면 따옴표가 어긋나
  **깨진 JSON**이 나온다.
- **sapkit**: `JSON.stringify`가 쓴다. 어떤 토큰이 와도 `JSON.parse`가 통과한다.
- **재현 (최소 합성 조각)**: 후행 주석이 있는 줄 — `WRITE lv_a. " remaining qty`.
  이 줄의 주석 토큰은 `" remaining qty`(따옴표로 시작한다 — 새 CLI로 확인)라서 구
  출력은 `"tokens":[""` 뒤에 따옴표가 하나 더 붙어 파싱에 실패한다. 코퍼스
  `synthetic/statements/lexical_forms.abap`에서 구 CLI로 `JSON.parse` 실패가 관측됐다
  (`harness/RECORDING.md` §2).
- **왜**: 출력 형식의 결함이지 판정이 아니다. 문장 유형도 토큰 열도 손대지 않는다 —
  같은 값을 **깨지지 않게 적을 뿐**이다.
- **판정**: 의도적 차이

## D-006 — 구 `parse --format summary`의 순서 비결정성을 승계하지 않는다

- **표면**: parse
- **구 vsp**: 유형별 건수를 Go map(`map[string]int`)에 담아 **그대로 순회해 출력**한다.
  Go의 map 순회는 의도적으로 무작위라 **실행마다 줄 순서가 바뀐다**(같은 파일 3회 실행
  → 3가지 순서. `harness/RECORDING.md` §2·§8-3의 관측이다).
- **sapkit**: 문장 유형 이름 **사전순**으로 고정한다. 같은 입력이면 언제나 같은 바이트다.
- **왜**: 출력이 실행마다 달라지면 diff를 뜰 수도, 게이트에 걸 수도 없다. 건수 자체는
  한 건도 바뀌지 않는다 — 줄의 **차례만** 정한다.
- **판정**: 의도적 차이

## D-007 — `parse --format json`에 `line`을 얹었다

- **표면**: parse
- **구 vsp**: 세 형식(`text`·`json`·`summary`) 중 **어느 것도 행 번호를 내지 않는다.**
  그래서 기준 채록본(`fixtures/baseline/parse.json` = (문장 유형, 행) 시퀀스)을 뜰 때
  CLI를 쓸 수 없어 분류기 패키지를 직접 부르는 일회용 Go 프로그램이 따로 필요했다
  (`harness/RECORDING.md` §2).
- **sapkit**: `{"type": …, "line": …, "tokens": […]}` — 구 키 둘을 그대로 두고 `line`을
  더한 **상위집합**이다. 값은 채록 규약과 같은 `tokens[0].row`이고, 토큰이 없으면 0이다.
- **왜**: 행이 없으면 새 CLI의 parse 표면을 기준 채록본과 **맞댈 수가 없다.** 대조가
  불가능한 표면은 「판정 동등성」을 주장할 근거가 없어진다. 실제로 이 키 덕분에
  parse 47/47 갈림 0을 CLI만으로 확인했다.
- **판정**: 의도적 차이

## D-008 — exit code가 결함(1)과 사용·입력 오류(2)를 가른다

- **표면**: lint · parse · analyze · check
- **구 vsp**: cobra의 `RunE`가 오류를 돌려주면 무엇이든 **exit 1**이다. 「Error 심각도를
  찾았다」와 「파일을 못 읽었다」·「인자를 잘못 줬다」가 같은 값으로 나온다.
- **sapkit**: **0 통과 · 1 결함 · 2 사용·입력 오류**로 셋을 가른다. 결함을 내는 표면은
  `lint`(Error 심각도)와 `check`(미해결 Z·Y·$ 인클루드)뿐이고, `parse`·`analyze`는
  읽히면 언제나 0이다.
- **판정 자체는 그대로다**: `lint`의 1은 여전히 「Error 심각도가 하나라도 있을 때」이며,
  읽히는 입력에 대해서는 구 exit code와 값이 같다. 기준 채록본
  `fixtures/baseline/lint.json`의 `exit_code`와 **47/47 일치**한다(대조 실측).
  달라지는 것은 **판정을 내지 못한 경우**뿐이다.
- **왜**: spec §2의 exit 계약이 「통과 0 / 결함 비-0 / 사용·입력 오류 비-0」으로 셋을
  나눠 적는다. 부르는 쪽이 "검사가 결함을 찾았다"와 "검사가 아예 돌지 못했다"를
  구분하지 못하면 자동화에서 후자를 전자로 오독한다.
- **판정**: 의도적 차이

## D-009 — `check`는 신설이라 구 판정 기준이 없다

- **표면**: check
- **구 vsp**: **대응물이 없다.** 프로젝트 트리의 인클루드 정합을 보는 명령이 없었다.
- **sapkit**: 디렉터리의 `.abap`을 전부 parse해 `INCLUDE` 문을 모으고, abapGit 명명
  관례(`<이름>.prog.abap` · `<이름>.fugr.abap` · `<이름>.abap`, 네임스페이스 `/`는 `#`)로
  트리 안의 파일과 맞춘다. 못 찾은 것 중 **첫 글자가 Z·Y·$인 것만 결함**(Error →
  exit 1)이고 나머지는 정보 수준이며, `INCLUDE … IF FOUND`는 **결함이 아니다**.
  `INCLUDE STRUCTURE`·`INCLUDE TYPE`은 DDIC 구조 포함이라 인클루드 참조로 세지 않는다.
- **곁딸린 판단**: 네임스페이스는 **첫 글자로 문자 그대로** 본다. 그래서 고객
  네임스페이스 이름(`/ABC/ZFOO`)은 첫 글자가 `/`라 정보 수준으로 떨어진다. spec §2.4가
  「Z*·Y*·$*만 결함」이라고 적었으므로 넓히지 않았다 — 넓히려면 새 결정이 필요하다.
- **왜**: spec §2.4가 신기능으로 명시했다. 구 기준이 없으므로 판정의 근거는
  **직접 세운 픽스처**(`src/cli/__tests__/fixtures/check/`, 합성 이름만)다. 뒤에 이
  판정을 고치면 그것은 「구 vsp와의 갈림」이 아니라 **이 항목의 정정**으로 단다.
  `IF FOUND`를 결함으로 세지 않는 것은 구 엔진 결함 13-13의 교훈을 미리 반영한 것이다.
- **판정**: 의도적 차이
